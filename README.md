<p align="center"><b>Self-hosted uptime monitoring that keeps working when parts of it fail.</b></p>

Uptime-Canary runs as a small group of independent, headless Go nodes. Each node runs your checks, keeps its own history in SQLite, opens incidents and sends alerts. Nodes that can reach each other coordinate, so you normally get one alert per outage and destination instead of one per node. Nothing central has to stay up: there is no shared database, no quorum and no required dashboard. An optional React dashboard and public status pages read from any node you choose.

> - **Protocol 18, the PM2 check (merged through [PR #8](https://github.com/Narehood/Uptime-Canary/pull/8); development, no release binary):** a **PM2 process** check. Each assigned node asks the PM2 daemon already running on its own machine, as the account Canary runs under, whether every process with an exact name (and an optional namespace) is online. It only reads: it never starts a daemon or starts, stops or restarts a process, and only PM2 6.0.8 is read. The connection is explicit, a Unix socket in a given PM2 home (Linux) or Windows' fixed named pipe, so mixed Linux and Windows nodes need separate monitors. Access to the daemon's socket is a deployment prerequisite, and it gives anything running as that account full control of PM2. On Linux the node asks only a daemon whose effective user ID equals its own, so a daemon run by another account stays pending even when its socket is reachable. A containerized node gets no access to the host's PM2 automatically, only through explicitly provisioned access to the intended daemon's socket; the daemon's user ID as mapped into the container must match Canary's, and the PM2 home is the path where that home is mounted inside the container. On Windows the daemon must run as Canary's account, and from the pipe's first creation only Canary's account, SYSTEM and Administrators may have been able to create instances of it or change its security, which the node can't verify after the fact; other clients' read access to the pipe isn't barred. ## How it works

![Historical architecture illustration: three of about six independent headless Go nodes. Each runs 28 check types (push included), alerts, maintenance and groups, a management API, and its own SQLite database, and reaches monitored services and alert destinations (Discord, SMTP, Mailgun, Brevo, Mailchimp, webhooks) directly. Nodes sync configuration revisions, latest observations, incidents, receipts and heartbeats with every listed peer. Raw history and accounts stay on each node. Operators use the CLI or the optional dashboard, one node at a time.](docs/assets/architecture.svg)

*Historical illustration, not redrawn: it shows an earlier scope, with 28 check types per node, the alert providers of that time and a static dashboard that signs in to one node at a time directly. It doesn't show the current [check types](#check-types) (29 on `main`, 32 with the protocol-19 candidate), the chat and push channels or the dashboard server with its shared node list ([deployment options](#deployment-options)), which the points below describe.*

- **Every node is complete on its own.** One Go executable with its own checks, incidents, alerts, management API and SQLite file. It keeps working when its peers or the dashboard are gone.
- **Peers share current state, not history.** Configuration revisions and tombstones (monitors, groups, channels, maintenance, status pages, tags), latest observations, incidents, receipts and push heartbeats travel in bounded, resumable pages. Raw history and accounts never leave a node.
- **Monitors run where you place them.** A monitor keeps one stable ID across its nodes, so "down everywhere" and "down from one location" are different, visible facts.
- **Delivery comes first.** Nodes take turns per destination; one that sees another's receipt stands down. If nobody's receipt arrives, the next node sends. Duplicates are possible; missed alerts are what the design avoids.
- **The dashboard is a guest.** Nodes never depend on it, and it shows one node at a time. The development dashboard talks to a node directly. The dashboard container runs a server with its own accounts and a shared list of registered nodes, which it reaches itself, so browsers need only the dashboard's address. Either way the tab keeps your sign-in in memory only, and the dashboard stores no monitoring data.

## Quickstart

This runs one headless node on your machine. You don't need Docker. For step-by-step Docker, Portainer and testing setup, see the [Setup and Testing](https://github.com/Narehood/Uptime-Canary/wiki/Setup-and-Testing) wiki page.

**You need:** Go 1.27.3 or newer (the npm scripts use `CANARY_GO`, then a portable Go in `.canary/tools/go`, then `go` on your `PATH`), and Node.js 24 (24.13 or newer, below 25) with npm for the setup script, CLI wrapper and dashboard.

```sh
npm install
npm run init   # writes a private .env with random tokens; never overwrites an existing one
npm run dev    # builds the Go node and starts it at http://127.0.0.1:3100
```

Then either open the dashboard (below) or use the CLI:

```sh
npm run canary -- status                          # this node, peers, monitors, groups, incidents
npm run canary -- add examples/http-monitor.json  # check https://example.com
npm run canary -- monitors                        # current state, including the new monitor's id
npm run canary -- history <monitor-id>            # this node's latest checks, newest first
```

The CLI reads its token from `.env`. Only `/healthz`, sign-in (`/api/auth/status`, `/api/auth/login`), published status pages (`/public/status/<slug>`) and push heartbeats (`/api/push`, with a push token) work without an account; everything else under `/api/` needs one. There are no default credentials: the admin token in `.env` creates the first admin account on first start.

## The dashboard

```sh
npm run dev:web   # http://127.0.0.1:5173, while npm run dev is running
```

**Globalping** (protocol 12, development) asks the [Globalping](https://globalping.io) network to run one measurement from a probe matching your location and reads its result.

![New-monitor form with Globalping chosen: a note that the target, location, path, query and request headers are sent to Globalping and its probe while the API token stays on the nodes, then the Ping/HTTP/DNS choice, the URL, a probe location of Frankfurt+AWS, the method and HTTP/2 options, and the response conditions with the keyword healthy.](docs/assets/dashboard-globalping.png)

- **What is shared.** The target, location and, for HTTP, the path, query and request headers (including an Authorization header) go to Globalping and the probe it picks, which may keep or publish measurement data under their own policies. The optional API token and API CA certificates stay on your nodes; viewers see neither the options nor an HTTP target's path and query.
- **What counts.** Target and resolver failures are down. Authentication, quota, API errors, offline probes and Globalping-internal failures are **pending** by default, because they say nothing about the target; an opt-in treats them as down, as Uptime Kuma does. Latency is the probe's own measurement, never the API round trip.
- **Cost and timing.** Every assigned node creates its own measurement on each check, and each one counts against your Globalping limit or credits, even when a check times out. The check's timeout covers creating and polling the measurement; the form recommends the probe timeout plus 10 s. Uptime-Canary doesn't verify where a probe is.

**System service** (protocol 16, development; local Windows runs and hosted CI on `256c7f2`, no release) asks each assigned node's own service manager about one service, by its internal name. The backend contract is in [system services](docs/system-services.md).

- **Where it runs.** Every selected node checks its own operating system, never another host. Linux nodes ask systemd about the unit, appending `.service` when the name doesn't already end with it (`sshd` reads `sshd.service`); Windows nodes ask the Service Control Manager, with read-only access, for the name as typed. Nothing is started, stopped or changed, and no credentials are involved.
- **What counts.** Running (systemd: active) is up; stopped or not installed is down. A node that can't read a service manager (none present, no permission, an unsupported OS, all its check workers busy, or a manager that doesn't answer within the check's timeout) reports **pending**, which never recovers an outage. Latency isn't measured and shows as a dash; a timeout of about 5 s is plenty.
- **Names.** 1–256 ASCII characters: a letter, digit or underscore first, then also dots, hyphens and `@` (for example `getty@tty1.service`). Use the internal name, not the display name: `Spooler`, not "Print Spooler". Spaces, paths, quotes and patterns are refused, so a Windows service whose internal name has other characters, such as a SQL Server named instance (`MSSQL$NAME`), can't be monitored. Changing the name, even from `sshd` to `sshd.service`, starts a new check.
- **Containers.** The node images are ordinary Alpine containers with no access to the host's systemd or Windows services, so a containerized node reports pending for this check. As with Uptime Kuma's system-service monitor, run the node directly on each machine whose services you want to watch. Uptime-Canary doesn't add host mounts, sockets or privileges for this.

**Steam game server** (protocol 17, development; hosted CI passed on `e3e7507`, no release) checks whether a server is listed in Steam's game server directory. The backend contract and its evidence are in [Steam monitors](docs/steam-monitors.md).

- **What it checks.** Directory membership, not the game itself. Each assigned node resolves the host (IPv4 first, like the pinned Uptime Kuma monitor) and asks `IGameServersService/GetServerList/v1/` for exactly the resolved address and port. A valid answer that lists it is up. A valid answer without it, an empty list included, is down, and so is a host name that doesn't resolve. Nothing speaks the game's own query protocol (A2S), so a running server that Steam doesn't list is down, and a listed one can still refuse players.
- **What is shared.** Every selected node makes its own request, carrying the resolved address and port and your Steam Web API key, which travels as a URL query parameter. Use Steam's API or an HTTPS endpoint you trust: a custom endpoint, and any proxy, can read the key. Plain HTTP needs an explicit opt-in. Extra CA certificates (up to 128 KiB) are added to the system roots for the API's HTTPS connection only, and verification can't be turned off. The dashboard keeps the key masked everywhere outside its own field, including the JSON preview with credentials shown, the detail page and the conflict view. Viewers receive no Steam options; the address isn't secret and stays visible.
- **What counts.** An unreachable or timed-out API, an error status (rate limits and refused keys included), a redirect or an unreadable answer is **pending** by default, because it says nothing about your server. An opt-in counts these as down, as Uptime Kuma does; a check the node itself cancels still stays pending.
- **Latency.** After a positive listing the node sends one ICMP echo (32-byte payload by default; 0 to 65,500, and 0 is kept) and shows its round trip only when a reply arrives. A lost reply, or a node without ICMP permission, shows a dash and the listing still counts. The API's response time is never shown as latency. Measurement can be turned off.
- **Cost and changes.** Each node calls the API on every check; the form shows the calls a day and warns above the 100,000 a day that Steam's Web API terms allow per key. The address, the key and every Steam option define the check, so changing any of them starts a new check generation; renames, pauses and conflict resolutions keep the stored options exactly.

**PM2 process** (protocol 18, development; merged through PR #8 after its final head passed every hosted gate, actual PM2 6.0.8 on Linux amd64 and arm64 included, while the first hosted run's failures stay on record (validation table); no release; scope in [PM2 monitors](docs/pm2-monitors.md)) asks each assigned node's own PM2 daemon about the processes with one exact name. Actual Windows PM2 interoperability is unverified.

- **Where it runs.** Every selected node connects, as the account Canary runs under, to a PM2 daemon that is already running on its own machine, never another host's, and only reads its process list. Nothing starts a daemon or starts, stops or restarts a process, and there are no user, privilege, shell or command settings. On Linux you give the daemon's PM2 home as one absolute path (no `~` or `$VARIABLES`, which the node never expands and refuses; the node opens `rpc.sock` inside it, at most 107 bytes in all); on Windows the node uses PM2's fixed local named pipe, so there's no path. The connection is part of the monitor, so Linux and Windows machines need separate monitors, and every node of one monitor uses the same home.
- **Access.** Letting Canary's account reach the daemon's socket is a deployment step. That access lets anything running as that account control PM2 fully, even through a read-only mount. On Linux the node asks only a daemon whose effective user ID equals Canary's own: a daemon run by another account stays pending even when its socket is reachable. A node in a container gets no access to the host's PM2 automatically; it needs explicitly provisioned access to the intended daemon's socket, the daemon's user ID as mapped into the container must match Canary's, and the PM2 home you enter is the path where that home is mounted inside the container. On Windows the daemon must already run as Canary's own account, and from the pipe's first creation only Canary's account, SYSTEM and Administrators may have been able to create instances of it or change its security; this is about who could serve or reconfigure the pipe, not which clients connect to it, and other clients' read access isn't barred. The node is pending when the daemon's account or the pipe's present owner and permissions don't fit, but it can't see their history, so this is a deployment prerequisite: tightening a pipe that was once more open isn't enough. [PM2 monitors](docs/pm2-monitors.md) explains this trust boundary.
- **What counts.** Up when every process with that name (in the namespace, if you set one) is online. Down when any of them is stopped, stopping, launching, errored or waiting to restart, or reports PM2's `one-launch-status`, or when no process with that name is listed in the chosen namespace (in any namespace when none is set); retries ride out a restart. **Pending** when the node gets no definite answer: no daemon at that connection; a daemon run by another account, or on Windows a pipe whose present owner or permissions don't fit; no permission to open the socket; a connection its system doesn't use, or a system other than Linux and Windows (macOS and other Unix systems always stay pending); a daemon that isn't PM2 6.0.8; an unreadable answer; a state it doesn't know; check workers that are busy or fail; or no answer within the timeout. A definite down on one process outweighs an unknown one, pending is never inverted, and it never recovers an outage. Latency isn't measured and shows as a dash.
- **Names.** The target is the process name exactly as `pm2 list` shows it, case, internal spaces and punctuation included; `3` is a process named "3", never PM2 id 3 or a PID. Names and namespaces are 1–256 bytes of text without control characters or surrounding spaces. They are identifiers, not secrets; the PM2 home is hidden from viewers and masked in the editor's JSON preview and the conflict view until you show it.

**Tailscale ping** (protocol-19 candidate, **not accepted**; local Windows evidence only; contract in [Tailscale checks](docs/tailscale-monitors.md)) asks each assigned node's own Tailscale client to ping one peer.

- **What it checks.** Tailscale's own peer ping over the tailnet, one attempt that doesn't wait for a direct path, not ICMP. One reply, direct or through a DERP or peer relay, is up, with the round trip the client reports as latency; the client confirming that its ping timed out is down. A missing client, a daemon that isn't running or signed in, an unknown peer, the node itself as the target, unexpected output, busy check workers or the timeout is **pending**, which is never inverted and never recovers an outage. There's no fallback to ICMP.
- **What each node needs.** An installed client and a running, authorized daemon on the intended tailnet. Linux nodes use `/usr/bin/tailscale` or `/usr/local/bin/tailscale`, Windows nodes `Tailscale/tailscale.exe` under Program Files; no other path can be set, and other systems stay pending. Canary never installs, starts, signs in to or configures Tailscale. The Alpine node image has neither the client nor the daemon, and a container gets no access to the host's Tailscale by itself.
- **Target.** A literal IP address or an ASCII DNS or MagicDNS name, without a URL, port, flags or shell syntax. Raw client output, peer names and routes never reach observations or alerts.

**Real browser** (protocol-19 candidate, **not accepted**; actual Chromium ran locally on Windows only; contract in [real browser checks](docs/browser-monitors.md)) loads a page in a Chromium browser service you run.

- **Where it runs.** No node or dashboard image contains a browser, and Canary starts none. Run a dedicated, trusted Chromium with its own sandbox and network and resource limits, never someone's everyday browser or profile, with its DevTools endpoint reachable from every assigned node and nowhere else: whoever reaches that endpoint controls the browser. Give either its full `ws://` or `wss://` DevTools address or an `http(s)://` origin whose `/json/version` names a WebSocket on the same origin. An optional bearer token goes only to the browser service, never to the page; redirects and environment proxies aren't used. The endpoint and token are private settings, hidden from viewers.
- **What counts.** Each check opens a fresh private browser context and page with downloads denied, and closes them afterwards. Up is a main document with a 2xx or 3xx status once the page is network-idle; a failed navigation, a download or any other status is down; an unavailable or incompatible browser, an authentication or transport failure, a malformed reply, a full node (two browser checks at a time), the timeout or a failed screenshot is **pending**. Latency is page-load time including an optional wait (0–30,000 ms), not a network round trip. There are no scripts, steps, selectors, logins or saved profiles.
- **Screenshots.** Opt-in 1024×576 PNGs of at most 192 KiB. Each node keeps only its own newest capture for the current check, never replicated, published or sent in alerts; editors and admins see it on the monitor's page, marked "Older capture" when it predates the latest result. Changing the check, turning capture off or a configuration conflict removes it.

**GameDig game server** (protocol-19 candidate, **not accepted**; local Windows evidence only; setup and contract in [game server checks](docs/game-server-monitors.md)) asks your GameDig query service to query one game server.

- **Where it runs.** GameDig runs in a separate, optional query service, not in the node: the node and dashboard images contain no GameDig. Build it from `Dockerfile.game-query` (the Compose `game-query` profile), or pull `ghcr.io/narehood/uptime-canary-game-query` with the standalone `deploy/portainer-game-query.yml` stack after checking that its package has a matching tag readable without credentials; a publishing workflow alone doesn't make an image available ([published images](#published-images)). Give it its own `CANARY_GAME_QUERY_TOKEN`, without which it won't start, and keep its API private. The service queries from its own network, so nodes sharing one service share its vantage and its availability; it runs two queries at a time and refuses more.
- **What counts.** A matching reply is up, with GameDig's measured round trip; a completed GameDig query failure is down; an unavailable service, a refused token, a malformed reply, a full service or the timeout (the service gets three quarters of it) is **pending**. No other GameDig options, scripts or modules can be set.
- **Settings.** The game comes from GameDig 5.3.3's pinned catalogue of 358 IDs, which isn't evidence that every game works. The address is one host name or IP; the port is optional when the catalogue lists a default and required otherwise, and "Only query this port" stops GameDig trying other ports. A game token (such as a Terraria TShock REST token), the service address and the service token are private: hidden from viewers and masked in previews. Plain HTTP to the service needs an explicit opt-in.

**Descriptions, cloning and new options** (protocol-19 candidate, **not accepted**):

- **Descriptions.** A plain-text note of up to 8,192 bytes for the people using the dashboard. Everyone signed in sees it, viewers included; it's never published or sent in alerts, and changing it never starts a new check.
- **Cloning.** **Clone** on a monitor's page opens the form as a copy with every setting, including private ones (passwords, tokens, keys, headers, bodies, certificates, service addresses) and fields the form doesn't show, and the form says so. A push copy gets its own new push token; a node refuses a push token another monitor already uses.
- **Edits keep what forms don't model.** Fields a newer node stored on monitors, channels, tags and maintenance windows survive edits made in these forms (a maintenance window's unknown schedule fields only while its schedule type is unchanged).
- **DNS, WebSocket and TCP.** SRV, SOA and CAA checks list expected records one per line; SOA and CAA need an explicit resolver, which each node asks directly. WebSocket checks can offer up to 16 subprotocols, optionally require the server to pick one, and use OAuth2 client credentials like HTTP (hidden from viewers). A TCP check can require a valid TLS handshake right after connecting.

## Alerts and channels

A channel is a reusable destination; a monitor lists up to 16 of them. Each email recipient is a separate destination with its own retries, outcome and receipt; a chat, push or webhook channel is one destination.

| Provider | Accepted when | Configuration |
| --- | --- | --- |
| Discord | Discord saves the message (`wait=true`) | Channel webhook URL |
| SMTP | The server accepts DATA | STARTTLS (default), implicit TLS, or an unauthenticated plain relay |
| Mailgun | The API accepts the message | API key, domain, US or EU region |
| Brevo | The transactional API accepts it | API key |
| Mailchimp Transactional | Mandrill reports sent/queued/scheduled per recipient | API key (not a Marketing key) |
| Webhook | Any 2xx | URL, optional bearer token, `Idempotency-Key` header |
| Slack *(protocol 13)* | Slack answers exactly `ok` | Incoming-webhook URL (the URL is the credential) |
| Telegram *(protocol 13)* | `ok:true` with a message ID for the configured chat | Bot token, chat ID or public @channel, optional forum topic, silent, protected and no-preview switches |
| ntfy *(protocol 13)* | A message ID for the configured topic | Topic, ntfy.sh or your server, no login, access token or user login, priority 1–5, tags |
| Gotify *(protocol 13)* | The server returns the created message | Your server URL, application token, priority 0–10 |
| Pushover *(protocol 13)* | `status:1` with a request ID | Application token, user or group key, optional device and sound, priority −2 to 2; emergency repeats every 30 s–3 h for up to 3 h |

The five chat and push providers send a plain-text title and message, never HTML, with the same placeholders as email templates. Built-in wording that is too long is shortened and ends with “[truncated; see monitor details]”; your own templates are sent exactly and fail as `invalid_message` if they expand past the provider's limit. HTTPS is required unless you explicitly allow plain HTTP for a configured server. A destination follows the channel and its route, not the credential: rotating a bot token, ntfy login or Pushover application token keeps receipts, while a different chat, topic, user key or device is a new destination. Gotify tokens don't identify their application, so alert a different Gotify application from a new channel.

**Accepted means the provider acknowledged the request**, not that a message reached an inbox or a device. Delivery status never includes provider bodies, addresses or secret URLs. Partitions and crashes can produce duplicates. SMS is planned later. Details: [notifications](docs/notifications.md).

**Defaults, adding to monitors and unsaved tests** (protocol-19 candidate, **not accepted**). A channel marked **Default for new monitors** is preselected on every new monitor while it's enabled, and each monitor can still clear it; existing monitors change only when you ask. **Add to monitors** adds a channel to up to 200 chosen monitors in one step: the node changes all of them at the revisions shown, or none if any changed meanwhile, and keeps each monitor's other channels and check generation. **Test these settings** sends one real message with what's in the channel form, disabled or unsaved, without saving it or creating an incident or receipt, and asks first. The first-release priority stays Discord, SMTP, Mailgun, Brevo and Mailchimp Transactional among the eleven native providers.

## One alert for a shared outage

![Two panels, each with a user-defined group containing an outage monitor and three dependent monitors, all down. Left: the outage monitor's alert is delivered, so the receiver gets one alert and the dependents hold theirs back while still recording. Right: the outage monitor's alert isn't delivered, so after their grace period the dependents alert on their own.](docs/assets/grouping.svg)

Groups are yours to define: names, nodes, and an optional **outage monitor** with a grace period. While the outage monitor has a fresh failure and its alert reached a destination, dependent monitors hold their alerts **to that destination**; other destinations fail open after the grace period. Checks, history and incidents continue throughout. Uptime-Canary doesn't guess whether a failure was power, internet, VPN or the host.

Protocol 11 (development) lets a group sit inside a **parent group** for an overview. A parent's health combines the current results of its own monitors and every nested group (down, then unknown, then pending, then up; an empty group is pending). Parent links don't extend alert holds or maintenance: both still follow each monitor's own group. A missing parent, a cycle or a conflicting version makes that part of the tree unknown until it's repaired. Details: [group hierarchy](docs/group-hierarchy.md).

## Status pages

![A public status page titled Service status: "All systems operational", an Identified announcement called Scheduled work about a database upgrade, and a Web section where the Website service is operational with a "production: eu" tag.](docs/assets/status-page.png)

Every node serves published pages as JSON at `/public/status/<slug>`, without an account, cookie or query secret. Pages contain only what you type: page and section titles, a public name for each selected monitor, announcements, and optional certificate dates and public tags. Private names, IDs, targets, errors and node details are never published, and unknown is never shown as up. The dashboard's status-page editor builds a shareable link such as `https://dashboard.example.com/#/status/services?node=https://canary-1.example.com`; visitors can switch to another listed node if one is unreachable. On the dashboard server, links and badges name only the dashboard's own address and a saved node registration (`?registration=<id>`, a public selector, not a credential); the server reads the page from that registered node without any management credential (see [one address for the browser](#deployment-options)). Managed custom domains, custom CSS and email or webhook subscriptions aren't available yet; the protocol-19 candidate adds typed presentation and an announcement feed (below). Details: [status pages](docs/status-pages.md) and [tags](docs/tags.md).

**Presentation and RSS** (protocol-19 candidate, **not accepted**). The editor's **Appearance** card sets the theme for visitors who haven't chosen one, an accent color (links and buttons use it only where text stays readable, 4.5:1), an `https://` logo that every visitor's browser loads from that server (the node never fetches it, and the editor loads a preview only when asked), a footer, how often open pages refresh, and optional Markdown for the description, footer and announcements: bold, italic, code, lists and `http(s)` links only; HTML, scripts and images stay plain text. These are typed settings only, never CSS, HTML or script. **Public address and RSS** records the address visitors open, which the node never fetches and which configures no DNS, TLS or proxy, and an opt-in RSS feed of the page's announcements, newest first, linking to that address; it never carries incidents, history, monitors or private names.

**Published 24 h history** (protocol 15, development; accepted locally on Windows, then hosted CI passed on `e12ba9e`; no release). In the editor, tick **24 h history** for a service to show visitors that service's last 24 hours as the answering node observed them: availability (up ÷ (up + down) time), coverage (share of the 24 hours with a known result) and an hourly strip with a table of the same figures. It's off by default, and pages without it save exactly as before. History is local to the node answering the visitor: nothing is merged across nodes, gaps and pending time are never counted as up, maintenance changes neither figure, percentages are truncated so a failure never rounds to 100.00%, and it isn't an SLA. Ticking it also discloses when outages happened. A node that doesn't run the check, or can't answer within its budget, shows the history as unavailable; the current state stays separate and is never made healthy by past up time. Details: [published availability](docs/public-availability.md).

**Badges** (protocol 11, development). Every node also serves `/public/badge/<slug>.svg` for a published page, or `?group=<section ID>&monitor=<public name>` for one service, with no account or token:

<p><img src="design/badges.svg" alt="Six status badges at actual size: up, down, pending and unknown, then down and up each with an extra maintenance segment." width="640"></p>

A badge shows the current state only: unknown when results are stale, missing or paused, and an extra maintenance segment that never hides a failure. A service that publishes its 24 h history (protocol 15, development) also answers `&metric=uptime`, a "24h observed" badge with the serving node's availability and coverage, or "unavailable" when that node can't answer; there's no whole-page figure. Two services with the same public name in one section get no badge, and changing the page address, a section ID or a public name breaks existing embeds. The dashboard's Share dialog and the public page copy ready-made Markdown or HTML. Details: [badges](docs/badges.md) and [badge design](design/badges.md).

**Dashboard server: its own accounts and one shared node list (merged through PR #11).** The dashboard container runs the Go dashboard server (`canary dashboard`), which follows the accepted model in the [contract](docs/dashboard-control-plane.md): the dashboard owns its accounts, sessions and a registry of nodes shared by every account, in its own SQLite database, separate from every node's.

1. **First owner.** Open the dashboard. While it has no owner, the server prints a private setup code in its log at start and keeps it in `/identity/setup.code`. Enter an account name, a password of 12 to 128 characters and that code to create the first administrator, and the dashboard signs you in. The code stops working once the owner exists; later accounts are created by an administrator on the Accounts page. No node address, node account or running node is involved.
2. **The bundled node.** After sign-in, Nodes lists every registered node. With `CANARY_LOCAL_NODE_URL` and `CANARY_LOCAL_NODE_TOKEN` set (`compose.yaml` and the combined stack supply `http://node:3100` and that node's `CANARY_ADMIN_TOKEN`), the server registers that node itself, showing it while it's being added and while the node starts; it can't be removed in the dashboard. A standalone dashboard can leave both blank and starts with an empty list.
3. **Add node.** An administrator enters a label, the address the dashboard server reaches the node at (an HTTP(S) origin without a path, such as a VPN address) and an admin credential for that node. Verifying is read-only: the server signs in to the node, reads its identity and shows the node ID it proved, and the check is valid for 2 minutes. On confirmation the server first saves three new role credentials, encrypted, then asks the node to create one dedicated admin, editor and viewer account for this dashboard in a single step, so a lost answer can be retried without leaving untracked accounts. An unfinished addition or removal stays visible with Retry. The server keeps the enrollment credential, encrypted, only until enrollment completes; the page clears it after each attempt.
4. **Use.** Choosing a node shows its monitors, incidents and settings with the same sign-in. The server sends each request to the saved address with that node's credential for your dashboard role, so viewers get the node's own secret redaction, editors change monitoring, and administrators also manage accounts and nodes. Viewers and editors see the list without addresses. Removing a node finishes at once only when the node confirms the revocation; otherwise it stays as Removal unfinished and the server keeps trying.

A node's `CANARY_ADMIN_TOKEN` is an enrollment credential, not your dashboard password, and node accounts aren't copied into the dashboard. Existing node accounts, databases, identity volumes and tokens stay as they are, and registering a node changes none of its monitors, peers or HA settings; peering stays explicit through `CANARY_PEERS`. On the node, the dashboard's accounts appear as `dashboard-<registration>-<role>`, and the node refuses to change their role or credential: on `main` a refused credential is repaired by removing and re-adding the node, because that dashboard has no credential rotation. The protocol-19 candidate (**not accepted**) adds three administrator actions that keep the registration ID, any selection of it and its public links: **Edit** renames an entry, offline ones included, or moves it to a new address once the server has proved the same node and every saved role credential there (the bundled node's address stays deployment-managed); **Rotate access** replaces the three role credentials in one step on a node that advertises the capability, revoking the old tokens and sessions, optionally with a current administrator credential from that node, and refuses before changing anything when the current credentials are known to be refused or a role account is missing; and **Recover access** finishes an update left as "Updating node access" with a current administrator credential, keeping the saved desired credentials. Rotation never recreates a deleted role account ([coordinated upgrades](docs/upgrades.md)). Only nodes built from this source can be added, the bundled one included; an older node is refused before anything on it changes. Limits: 64 registered nodes and 16 pending verifications per dashboard; per node, the three accounts count toward its limit of 64 accounts, and it remembers up to 1024 removed enrollments.

**Status:** merged through PR #11 as `103f5c4`, after the hosted gates passed on its final head `83596cc` (status box); not a release. On source checkpoint `2f69dbac…` (2026-10-24, Windows amd64, local) the whole `canary` package passed with `go vet` (1,088 passing events, 0 failures, 2 expected Windows question-mark skips), and so did the three type-checks, 139 pure check groups and the script and Python syntax checks ([validation](#checks-and-validation)). Earlier records keep their own exact sources: identity controls on `f728ae73…` (setup without a node, owner races, restart, roles, logout, last-admin protection, transaction rollback; component evidence, see the [contract](docs/dashboard-control-plane.md)), a static checkpoint on `0fd714e0…` (130 pure check groups, 12.234 s) and a browser run on `b937c27e…` (169/169), which predates the Push repair below and doesn't cover `2f69dbac…`. Acceptance then still needed the browser checks on current source and the new head's process, container and hosted gates (native Linux and Alpine, arm64, race and actual PM2), with the unchanged 22 process proofs and their deadlines; the browser checks then passed 170/170 on `2f69dbac…` ([contract](docs/dashboard-control-plane.md)) and the hosted gates on `83596cc`. Actual NetBird or Tailscale interoperability is unverified, and neither a release nor HA parity is claimed: dashboard accounts and the registry live on one dashboard server, with no HA or failover. Images published from `main` through `187afae` don't contain the dashboard server (their web image is the earlier static dashboard); images published from `103f5c4` do, and the protocol-19 candidate's registry maintenance needs images published from its own source after an approved merge; the [packages](https://github.com/Narehood/Uptime-Canary/packages) and the [Container images workflow](https://github.com/Narehood/Uptime-Canary/actions/workflows/container-images.yml) show which tags exist ([published images](#published-images)).

**One address for the browser.** The path is browser → dashboard server → each registered node's private address. The server itself (no nginx) serves the dashboard's files and its API on one origin, generates `/canary-config.js` and marks the page it serves as its own, so the dashboard keeps its own sign-in even if a proxy blocks that script. Browsers need only the dashboard's address: no node API port has to be published to them or be reachable from them, nodes on a NetBird or Tailscale network only need to be reachable from the server, and no separate external `/api` route is needed. Only an administrator's Add node supplies a node address, which the server verifies before saving; a monitoring request names a saved registration (the `X-Canary-Registered-Node` header), never an address. The server doesn't forward `/internal/` peer traffic or node account routes, sends a node no browser cookie, credential or origin, refuses redirects, verifies HTTPS certificates and bounds request and answer sizes, time and concurrency. Each node request names the node ID the server proved, and an answer from another node at that address is refused and shown as such. A node that refuses the dashboard's credential is a 502 with a fixed message, never a 401, so it can't sign you out of the dashboard. A stopped or unreachable node never blocks dashboard setup, sign-in or the other nodes; its card says it isn't answering. `/healthz` answers while the server runs and `/readyz` while its account store is usable; the container's health check reads `/readyz`. The server refuses a browser request whose origin isn't exactly one of `CANARY_DASHBOARD_ORIGINS` (`compose.yaml` and the templates set it from `CANARY_CORS_ORIGINS`; with neither, `http://localhost:18347` and `http://127.0.0.1:18347`). Nodes don't need the dashboard's origin in their own `CANARY_CORS_ORIGINS` for this, because the server's requests carry no browser origin; direct mode still does. Proxy and node setup: [Portainer](docs/portainer.md#sign-in-protected-reverse-proxies).

**Push heartbeats through the dashboard.** With a node selected, the Push form's `curl` example sends to the dashboard's address with that registration: `POST /api/push?registration=<id>` with the monitor's `Authorization: Push <token>`, or, where GET is accepted, `GET /api/push/<token>?registration=<id>&status=up`. This route needs no dashboard sign-in: the server removes the selector, forwards the push token but no dashboard credential or proxy cookie, and the node keeps its own token, rate and durability checks. The sending machine must reach the dashboard's address and, behind a sign-in proxy, pass the proxy's check, or send the same request without `registration` straight to the node on your private network; don't exempt `/api/` from the proxy for it. Without a selection, and in direct mode, the example is unchanged ([contract](docs/dashboard-control-plane.md)).

**Direct mode (development and static hosting).** The development server (`npm run dev:web`) and the built files on any other static host keep the earlier direct mode, which remains supported: the sign-in screen asks for a node API address, the browser calls that node's management API itself (so it needs a route to it, and the node's `CANARY_CORS_ORIGINS` must list the dashboard's origin), you sign in with that node's account, and the dashboard can switch to a peer's address. The source copy of `/canary-config.js` leaves the server modes off; only the dashboard server's generated script and page marker turn them on. On the dashboard server the sign-in screen has no address field and ignores an address remembered from direct mode, endpoint switching and other peer-address actions are hidden (you choose a registered node instead), status-page links and badges use the dashboard's address, and the dashboard refuses to contact any other origin, including node addresses in older status-page links, with a message saying so.

**Earlier gateway step (replaced, historical).** Earlier uncommitted work on this branch had the dashboard container forward `/api/` and `/public/` through nginx to one entry node set with `CANARY_API_UPSTREAM`, signing in with that node's accounts. The dashboard server replaced it before that container was validated: there is no `CANARY_API_UPSTREAM` setting any more, and no current container provides that gateway-only mode. The dashboard keeps its client side, with its fixtures (`scripts/dashboard-gateway-pure.mjs` and the gateway part of `scripts/node-login-copy-pure.mjs`), for a server that sets only the gateway flag.

### Published images

**Check availability before deploying.** A configured publishing workflow isn't a publication. The repository's [packages](https://github.com/Narehood/Uptime-Canary/packages) list the tags that exist, and the [Container images workflow](https://github.com/Narehood/Uptime-Canary/actions/workflows/container-images.yml) shows the status of each run. Deploy without GitHub credentials only after a publication has succeeded and both packages allow anonymous pulls; until then, use images built from source through the overrides below. The templates in `deploy/` pull two images from GitHub Container Registry, so neither Portainer nor `docker compose -f deploy/…` builds anything:

| Image | Default reference |
| --- | --- |
| Node | `ghcr.io/narehood/uptime-canary-node:latest` |
| Dashboard | `ghcr.io/narehood/uptime-canary-web:latest` |

- **Publishing.** In the GitHub Actions publisher, pull requests build both images without pushing either. A push to `main`, or a manual run on `main`, pushes both as `sha-<commit>` (the full 40-character commit) and moves `latest` to both only after both builds have succeeded and while that commit is still the head of `main`. Its actions are pinned to full commit SHAs, and each image is labelled with its source repository and revision.
- **Pinning.** `latest` follows `main`. Set `CANARY_IMAGE_TAG=sha-<full commit>` to select that commit's tag for both images. Compose always pulls `latest`, even under the default `missing` policy, so each deploy takes whatever `latest` is at that moment, and hosts deployed at different times can run different builds. Peers must speak the same protocol, so for a coordinated upgrade pin every node to the same `sha-<full commit>` tag, or the same digest through the overrides below, and change it on all of them together. A `sha-` tag names the source commit, and a rerun of the publisher rebuilds it from that source; use a digest when every host must run the identical image.
- **Overrides.** `CANARY_NODE_IMAGE` and `CANARY_WEB_IMAGE` replace the whole reference, for example a tag in your own registry or a digest (`…@sha256:<digest>`), and take precedence over `CANARY_IMAGE_TAG`. `CANARY_PULL_POLICY` defaults to `missing` (pull only when the host lacks the image, except that Compose always pulls `latest`); set it to `never` for images you've preloaded or built yourself, on an offline host for example, so a missing image stops the deploy instead of starting a registry pull.
- **Platform.** Only `linux/amd64` images are planned at first. Native Linux arm64 binaries pass the native package workflow, but that doesn't produce or test an arm64 image, and building the images on an arm64 host is untested.
- **Visibility.** New GitHub packages start private. Until the repository owner has made both packages public (a one-time setting for each) and an anonymous pull has been checked, a pull without GitHub credentials fails.
- **Unchanged.** Node IDs, tokens, ports (API 3100, dashboard 18347, 8080 inside the dashboard container) and node volumes stay as they are; the dashboard server adds its own two volumes (below). The repository's `compose.yaml` still builds both images from your checkout.

**Existing Portainer stacks** used images built on the host as `uptime-canary-node:development` and `uptime-canary-web:development`. Redeployed from the updated templates without an image override, a stack pulls `latest` from the registry instead; keep the stack name so its volumes stay, and upgrade all nodes together. To keep using your own images, set `CANARY_NODE_IMAGE` and `CANARY_WEB_IMAGE` to those tags together with `CANARY_PULL_POLICY=never`.

The dashboard container publishes host port **18347** by default (`CANARY_WEB_PORT`), chosen to stay clear of ports common self-hosted apps use, such as 8080. Nothing stops another app from using 18347; if it's taken, set `CANARY_WEB_PORT` to a free port. Inside the container the dashboard server listens on 8080 and its health check reads `/readyz` there (the earlier static image ran nginx on 8080 and checked `/healthz`). Earlier CI records keep the ports and exact source they tested; validation of this host-port change is recorded with its pull request.

**Existing installations:** a `CANARY_WEB_PORT` you set explicitly keeps applying. Without one, the dashboard moves to 18347, but an existing `CANARY_CORS_ORIGINS` still names the old `:8080` origins (`npm run init` never rewrites an existing `.env`, and Portainer keeps your stack variables), so the browser's new origin is refused: by the dashboard server, which takes its allowed origins from that variable in `compose.yaml` and the templates, and in direct mode by each node. Either set `CANARY_WEB_PORT=8080`, or add the exact address you open the dashboard at, such as `http://localhost:18347`, to `CANARY_CORS_ORIGINS` for the dashboard (and on every node a direct-mode dashboard signs in to). Update that origin whenever you change the host port.

Every port listens on `127.0.0.1` by default. All images are Alpine Linux, build stages included; the node runs as an unprivileged user with `no-new-privileges`, and Compose grants `NET_RAW` only for ping. Each node needs its own volumes: `canary-data` at `/data` for the database and a separate `canary-identity` at `/identity` for identity state. Never share them between nodes, and keep the identity volume when you restore a database. Containers created before the identity volume existed need a one-time, stopped-node copy: see [backups](docs/backups.md).

The dashboard server has its own two volumes and never opens a node's: `canary-dashboard-data` at `/data` holds its account database with the node registry and the encrypted node credentials, and `canary-dashboard-identity` at `/identity` holds the AES-GCM key (`dashboard.key`), `setup.code` and its account store's origin state (`auth-origin`). Keep both, and keep the identity volume out of database backups. A dashboard database without its matching identity files refuses to start instead of generating a replacement key, and a wrong key is refused too. The node volumes `canary-data` and `canary-identity` are unchanged. Stopping or losing the dashboard doesn't stop any checks or alerts.

**Behind a sign-in proxy.** Behind an authenticating reverse proxy that sets its own session cookie, such as NetBird SSO, route the whole dashboard origin, full path included, to the dashboard container, and remove an older rule that sent `/api/` straight to a node. The dashboard's requests stay on that origin, so they carry the proxy's cookie and the proxy lets them through; the dashboard server never passes that cookie on and reaches each node with its own role credential. You still sign in to the dashboard: the proxy's session and identity headers don't create or authorize dashboard accounts. Keep the origin, such as `https://uptime.example.com`, in `CANARY_CORS_ORIGINS`, which the templates pass to the dashboard as its allowed origin. Peers in `CANARY_PEERS` and the CLI need node addresses the proxy doesn't gate. The dashboard never follows redirects, so when the proxy's session ends its requests fail rather than reaching the proxy's sign-in page, and the error suggests reloading. A full page reload goes through the proxy's sign-in again; then sign in to the dashboard again, because the tab keeps its credential only in memory. Signing out of the dashboard doesn't sign you out of the proxy. Interoperability with actual NetBird or Tailscale setups is unverified; the project's proxy checks use a synthetic cookie-gated proxy. In direct mode the proxy can instead send `/` to the dashboard's files and `/api/` (and `/public/`, for status pages and badges) to one node on that origin. Browsers send no cookies to a node on another origin, so nodes the dashboard switches to then need addresses the proxy doesn't gate.

## Run several nodes

Uptime-Canary is designed for a handful of nodes, about six, on different hosts. You list peers yourself; nodes don't discover each other.

1. Give every host its own `.env` with a unique `CANARY_NODE_ID` (choose it before the first start).
2. Copy the same `CANARY_CLUSTER_TOKEN` to every node.
3. List all other nodes in `CANARY_PEERS`, using private network or VPN addresses, and make the API reachable there.
4. Place monitors on nodes with `nodeIds`.
5. **Upgrade all nodes together.** Nodes reject peers that speak a different protocol version. With the [published images](#published-images), give every node the same `CANARY_IMAGE_TAG`. Back up first and follow [coordinated upgrades](docs/upgrades.md).

Peer sync and the management API use HTTP with bearer credentials and carry configuration that includes alert credentials. Keep them on a VPN or trusted private network, or put HTTPS in front of each node.

Peering and the dashboard's node list are separate: adding nodes to one dashboard doesn't peer them, and peers aren't added to a dashboard automatically.

## When things fail

![Four panels, each with three nodes and an alert receiver. 1, Connected: node 1 sends one alert and its receipt makes the others stand down. 2, Sender lost: node 2 sends after its stagger, with no quorum. 3, Partitioned: each side sends, so the receiver gets two alerts. 4, Healed: receipts and incidents merge without replaying old alerts, and one recovery is sent.](docs/assets/failure-behavior.svg)

| Situation | What the nodes do | What you receive |
| --- | --- | --- |
| **Everything connected** | The first node in line sends to each destination and syncs its receipt; the others stand down | One alert per incident and destination |
| **The sender dies or can't reach the destination** | No receipt arrives, so the next node in line sends | One alert, a few seconds later |
| **Network partition** | Each side decides and sends on its own | Duplicates are expected |
| **Partition heals** | Receipts, incidents and configuration merge; delivered alerts aren't resent | One recovery per destination |
| **Planned maintenance** | Checks and incidents continue; new alerts are held | Owed alerts after the window, if the outage continues |
| **A node can't measure** | It reports unknown, which never counts as up or down | No false recovery |
| **The dashboard is closed** | Nothing changes | Alerts as usual |

An incident opens on any fresh failure and recovers only when every assigned node reports a fresh success. Editing a monitor's name, interval, destinations, tags or group keeps an open incident; changing what is checked, pausing or deleting closes it administratively, without a recovery alert. The dashboard warns before you save such a change.

## Not yet implemented

- **Public history beyond 24 hours, whole-page uptime, rollups beyond 90 days and merged multi-node availability.** Observed time in the dashboard covers only the node you're connected to; published 24 h history (protocol 15, development) covers only the node answering the visitor.
- **Aggregate alerts for parent groups, inherited holds or maintenance, and nested sections on public pages.**
- **Shared Globalping measurements across nodes.** Each assigned node measures, and pays, separately; there is no leader, deduplication or shared result. Probe locations aren't verified, and target POST bodies, custom target CAs, client certificates, OAuth2 and redirect controls aren't available for Globalping checks.
- **Service checks on other machines or from containers.** A system-service check (protocol 16, development) reads only the node's own operating system: there's no SSH, WinRM or agent for other hosts, no host access for a containerized node, and internal names are limited to letters, digits and `_ . - @`. The PM2 check (protocol 18) and the Tailscale check (protocol-19 candidate) also read only the node's own machine and its local client or daemon.
- **PM2 beyond reading one local daemon.** The PM2 check (protocol 18) reads only an already running PM2 6.0.8 daemon on each node's own machine through one connection per monitor: no remote PM2, no restarting or other process control, no CPU, memory or restart-count conditions, and no targets by PM2 id or PID.
- **Game-server details, and direct game queries on `main`.** The Steam check (protocol 17, development) reads only Steam's directory: there is no A2S query, no player count, map or version, no check for servers Steam doesn't list, and no shared result across nodes (each node calls the API and uses the key itself). The GameDig check (protocol-19 candidate, not accepted) queries game servers only through your separately run GameDig 5.3.3 service, with no player, map or version conditions; its 358-ID catalogue isn't 358 tested games, and nodes sharing one service share its network vantage.
- **Browser scripting and some protocol options.** A real-browser check (protocol-19 candidate) loads one page: no scripts, steps, selectors, logins or saved browser profiles. Also not implemented: NTLM authentication, saved proxy profiles and SOCKS proxies, domain-registration expiry, Kafka AWS authentication and a WebSocket accept-header bypass ([parity inventory](docs/parity-audit.md)).
- **Status-page managed custom domains, raw CSS, history beyond the last 24 hours, email or webhook subscriptions or automatic incident publication.** The protocol-19 candidate's public address only records where visitors open a page; it configures no DNS, TLS or proxy, and its RSS feed carries announcements only.
- **SMS, providers beyond these eleven, and provider extras** such as Slack blocks, Telegram formatting, ntfy actions or attachments, and Pushover receipt polling.
- **Container images beyond `linux/amd64`, version tags and releases.** The planned publisher pushes only `latest` and `sha-<commit>` images for `linux/amd64` from `main`; there's no arm64 image, version tag or release.
- **Exactly-once alerts.** Duplicates are possible by design.
- **Replicated history or node accounts, automatic discovery.**
- **Dashboard HA, merged views and, on `main`, node credential rotation.** The dashboard server keeps its accounts and node registry on one server, with no replication or failover. It shows one selected node at a time, not monitors merged across nodes, and has no aggregate fleet monitors. On `main` a refused node credential is repaired by removing and re-adding the node; the protocol-19 candidate adds in-place rotation and recovery but never recreates a deleted role account. The bundled node can't be removed in the dashboard, and node accounts aren't imported.
- **Unbounded scale.** Coordination records are retained; storage, memory and catch-up costs grow over time. See [runtime coordination](apps/node-go/RUNTIME.md) and [shipping progress](docs/shipping-progress.md) for the remaining release work.
