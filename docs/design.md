## 1. Design principles

1. **Say where every fact comes from.** Each state answers *from which node, as of when, as seen by which endpoint*. The dashboard talks to one endpoint (Agreed). It never pretends to be a global, central view.
2. **Unknown is a real state.** A stale observation, an out-of-view peer or an unresolved config conflict shows as **unknown**: a dashed ring, plus hatching when out of view. It is never painted as up or down (Agreed).
3. **Location before verdict.** Every aggregate state sits next to its per-location evidence, and the wording separates *down everywhere* from *down from 2 of 6 locations* (Agreed).
4. **Quiet when healthy, loud when not.** Healthy cells are small checks. Problems get filled shapes, banners and the top of every list. On phones, healthy rows collapse to one line.
5. **Explain the mechanism when it matters.** Partitions, duplicates, candidates, conflicts and held-back alerts get one plain sentence at the point of impact. The UI never promises exactly-once delivery (Agreed).
6. **The dashboard is a guest.** It reads nodes; nodes never depend on it. Losing the web container or an endpoint is an explainable state, not an error page (Agreed).
7. **No hidden decisions.** Outage policy, revision, sender, candidate order, conflict heads and group dependencies are visible where they affect the outcome.
8. **Nothing is claimed before the node says so.** A save, delete or resolution is reported only after the endpoint acknowledges it, with the revision it returned (Proposed).
9. **Plain-spoken and calm.** Short sentences and everyday words. Identifiers appear in monospace.

## 2. Mental model and vocabulary

| Term in UI | Meaning | Source |
|---|---|---|
| **Node** | An independent runtime (scheduler, probes, SQLite, incidents, notifications, API). | `NodeView` |
| **Endpoint** | The node this dashboard currently talks to. Switchable. | `Overview.node` |
| **Dashboard account** | Control plane only: an account on the dashboard server, separate from every node's accounts; its admin, editor or viewer role applies to the whole shared node list. | the dashboard's `/api/auth/*`, `/api/accounts` |
| **Registered node** | Control plane only: an entry in the dashboard's shared node list, with a label, the node ID the server proved, the server-side address (admins only) and a state. Choosing one is a selection with the same sign-in, not an endpoint switch. | `RegisteredNode` |
| **In view / out of view** | Whether the endpoint can currently reach a peer. Out-of-view cells are hatched. | `NodeView.state`, `lastSeenAt` |
| **Location** | A node in its role as an observer of a monitor. | `Observation.nodeId` |
| **Observation** | A node's latest check result. *Fresh* means recent and taken on the current revision. | `MonitorView.observations` |
| **Monitor** | A check with a stable ID that is shared across its assigned nodes. | `Monitor.id`, `nodeIds` |
| **Revision** | An opaque config version. The UI shows the first 6 characters. | `Monitor.revision`, `Group.revision` |
| **Conflict** | Two or more revision heads after concurrent edits. Shown until someone resolves it. | `configConflict`, `/conflicts` |
| **Incident** | Records merged by monitor across nodes. Opaque IDs; no sequential numbers. | `IncidentView` |
| **Recovered / Closed after config change** | How a closed incident ended: every assigned location reported a fresh up, or the check was changed, paused or deleted. Only a recovery is green; the other closes without an up result or a recovery alert. | `resolvedAt`, `retiredBy`, `retirementReason` |
| **Receipt** | A successful notification send by one node. | `NotificationView` |
| **Candidate order** | Assigned nodes sorted by ID: the order in which nodes try to notify. | derived from `nodeIds` |
| **Duplicate** | More than one down (or recovery) receipt for the same incident. | derived |
| **Group** | A user-named set of nodes and monitors, optionally with an outage monitor. No built-in names or topology. | `GroupView` |
| **Outage monitor** | An ordinary monitor whose delivered outage alert stands in for the group's other monitors. | `Group.outageMonitorId` |
| **Grace period** | How long a dependent monitor's alert waits, from its own outage, for the outage monitor's evidence and delivery. | `Group.graceMs` |
| **Held back** | A dependent alert suppressed by its group. Checks, history and incidents continue. | `suppressedByGroupId`, `suppressionReason` |
| **Outage policy** | Milestone rule: any fresh failure opens an incident; recovery needs fresh up from every assigned node. | Agreed |
| **Channel** | A reusable notification destination set: Discord, Slack, Telegram, ntfy, Gotify, Pushover (the five chat and push providers are protocol 13, in progress), SMTP, Mailgun, Brevo, Mailchimp Transactional or a JSON webhook. | `NotificationChannelView` |
| **Destination** | One route inside a channel: one email recipient, or the whole chat, push or webhook channel. Each has its own retries, outcome and receipt. Bound to the channel ID plus the route, never the credential. | `destinationId` |
| **Delivery attempt** | A node's send effort for one destination: queued, sending, retrying, held, accepted, failed, cancelled, unknown or unavailable. | `DeliveryAttemptView` |
| **Accepted** | The provider acknowledged the request. Not proof of inbox, channel or device delivery. | Agreed |
| **Maintenance window** | Planned work that holds new alerts while checks, history and incidents continue. Never turns a result green. | `MaintenanceView` |
| **Status page** | A published page of operator-chosen public names; served by every node as JSON. | `StatusPage`, `PublicStatusPage` |
| **Tag** | A reusable label with a color, assigned to monitors with an optional value and public flag. | `TagView`, `MonitorTag` |
| **Push heartbeat** | A passive check: an external job reports up or down before a deadline. | `MonitorInput.push` |
| **Sample availability** | Up ÷ (up + down) samples in a window, from one node. Not a time-weighted uptime or SLA. A 0–1 ratio. | `LocalHistoryStatistics` |
| **Observed time** | How long the endpoint held a fresh local result in each state, per bucket. Time without one is unknown, never up. **Observed availability** = up ÷ (up + down) time; **coverage** = known time ÷ the window; both 0–100 %. Maintenance overlaps and removes nothing. Not an SLA. | `LocalAvailabilityHistory`, `ObservedTimeTotals` |
| **Parent group** | An optional organizing link between groups. It rolls up current health only; alert holds and maintenance still follow each monitor's own group. | `GroupInput.parentId` |
| **Health** | A group's current rollup of its monitors and nested groups: down, then unknown, then pending, then up; empty or all-paused is pending. Counts are current monitors, not uptime. Unknown with a reason, and no counts, when the hierarchy is missing a parent, cyclic or conflicting. | `GroupView.healthState`, `health`, `healthReason` |
| **Badge** | A public SVG image of a published page's state, or one service's, picked by public section ID and public name. | `/public/badge/<slug>.svg` |
| **Remote probe (Globalping)** | A third-party probe, picked per check by a free-form "magic" location, that measures the target for the node. Provider failures are pending unless the operator opts into down. | `MonitorInput.globalping` |

### 2.1 State vocabulary

Status shapes carry meaning and color reinforces it, so meaning never depends on color alone:

| Glyph | Shape | Color token | Used for |
|---|---|---|---|
| Up | filled circle + check | `good #0ca30c` | fresh up, connected peer, recovery receipt |
| Down | rounded square + ✕ | `critical #d03b3b` | fresh down, form errors |
| Warning | triangle + ! | `warning #fab219`, edge `#a86f00` | peers out of view, groups holding alerts, a mixed history bucket, endpoint not answering |
| Conflict | diamond + ! | `serious #ec835a`, edge `#b5532c` | config conflict heads |
| Unknown | dashed ring + ? | `neutral #898781` | stale, earlier revision, out of view, conflict-affected |
| Paused | ring + bars | neutral | `enabled: false` |
| Pending | ring + clock hands | neutral | a retry in progress, a container starting, a manual monitor without status; neither up nor down |
| Maintenance | wrench in a warning-wash tag | `--warning-wash` | `maintenanceIds` on a monitor or incident; shown beside the measured state, never instead of it |
| Not assigned | short dash | neutral | node does not run the monitor; an incident closed after a config change |
| Out of view | 45° hatch behind the glyph | `--hatch` | node not reachable from the endpoint |
| Alerts held | layers icon in a warning-wash tag | `--warning-wash` | `suppressedByGroupId` on a monitor or incident |

**Monitor aggregate chip** (Agreed semantics, Proposed wording; computed in `model.ts`):

| Chip | Rule | `MonitorView.state` |
|---|---|---|
| **Down · everywhere** | every assigned location has a fresh down (single-location monitors say *from node-id*) | `down` |
| **Down · n of m locations [· k unknown / not in view]** | at least one fresh down, not all | `down` |
| **Unknown · config conflict** | conflicting heads | any |
| **Unknown · k of m not in view / without fresh data** | no fresh down, some locations lack fresh data ("not in view" only when every such node is out of view) | `unknown` |
| **Up** | every assigned location fresh up | `up` |
| **Paused** | disabled | `paused` |

Sort order everywhere: Down everywhere → Down partial → Conflict → Unknown → Up → Paused. Within a level, monitors whose alerts are held back follow the others, so a group's root cause leads.

## 3. Information architecture

```
Rail (primary nav)                    Top bar (global context)
├─ Overview                           ├─ Endpoint button: "Viewing from <id>" · peers in view · switch (direct mode)
├─ Monitors ─ detail ─ edit ─ Tags    ├─ Search (/ or Ctrl/Cmd-K): names, targets, node IDs, IDs, tags, groups
├─ Groups ─ new ─ edit                ├─ Freshness: "Updated 3 s ago" / "Not answering" / "Signed out"
├─ Incidents                          ├─ Theme: system → light → dark
├─ Notifications                      ├─ You: account name · role · "on <endpoint>"
│   ├─ Channels ─ new ─ edit          └─ Sign out / Disconnect
│   ├─ Delivery attempts
│   └─ Receipts                       Public (no sign-in, outside the shell)
├─ Maintenance ─ new ─ edit           └─ #/status/<slug>?node=<address>[&node=…] (control plane: ?registration=<id>)
├─ Status pages ─ new ─ edit
├─ Nodes
├─ Configuration (conflicts)
└─ Accounts (admins only)
```

Hash routes keep the web container simple and never carry tokens or API data. The only route with a query string is the public status page, whose `node` parameters are public node addresses chosen by whoever shares the link (Proposed).

The bundle carries no build-time node address, credential or setting, so one dashboard image can serve every installation. The dashboard image runs the Go dashboard server (`canary dashboard`), not nginx: it serves the built files, generates a `/canary-config.js` with the gateway and control-plane flags on, writes its marker into `index.html`, and answers the dashboard's own account, registry and monitoring routes on the same origin, reaching the registered nodes itself, so the browser talks only to the dashboard's origin and never chooses a node address (§4.1, §4.10). In direct mode (the development server, or the built files on another static host, whose `/canary-config.js` leaves both flags off) the browser chooses the node at sign-in (§4.1). Earlier dashboard images served the files from nginx without proxying, and an intermediate, unvalidated step on the same branch forwarded through nginx to one entry node set with `CANARY_API_UPSTREAM`; neither is the current image, and that setting no longer exists. The dashboard image the publishing workflow builds, `ghcr.io/narehood/uptime-canary-web` (`latest`, or `sha-<commit>` matching the node image), relies on this; images published from `main` through `187afae` carry the earlier static dashboard, so the dashboard server needs images published from matching source. Configuring that workflow doesn't publish the image; which tags exist, and when a deploy can pull them without credentials, is covered under [published images](../README.md#published-images) in the README (Agreed).

| Route | Purpose | API sources |
|---|---|---|
| `#/overview` | What needs attention now, from this endpoint's view | `GET /api/overview` |
| `#/monitors`, `/new`, `/<id>`, `/<id>/edit` | List with state, type and tag filters; create; detail; edit; pause; delete | `overview`, monitor CRUD, `/history?from&to&limit`, `/statistics`, `/availability?from&to&stepMs`, `/notification-deliveries?monitorId` |
| `#/tags` | Tag catalog: name, color, usage | `/api/tags` CRUD |
| `#/groups`, `/new`, `/<id>/edit` | Groups as a tree: health counts, parent, dependency and what they hold back | `overview.groups` (with `healthState`, `health`, `healthReason`), group CRUD |
| `#/incidents` | Open and closed incidents with delivery, maintenance and suppression lines | `overview.incidents`, `notifications` |
| `#/notifications` | Channels: create, edit, test, delete | `/api/notification-channels` |
| `#/notifications/deliveries` | Every delivery attempt known to the endpoint, per destination | `/api/notification-deliveries` |
| `#/notifications/receipts` | Successful sends with duplicate marking | `overview.notifications` |
| `#/maintenance`, `/new`, `/<id>/edit` | Planned windows with the node's computed current and next window | `overview.maintenance`, maintenance CRUD |
| `#/status-pages`, `/new`, `/<id>/edit` | Publication editor, share links and badge links | `/api/status-pages`; badge previews from `/public/badge/<slug>.svg` |
| `#/status/<slug>?node=…` (control plane: `?registration=<id>`) | The public page itself, with an embed-a-badge panel | `GET /public/status/<slug>` and badge images, without a credential; on the control plane from the dashboard's origin, which reads the saved node |
| `#/nodes` | Endpoint path, peer state from the endpoint, endpoint switching (direct mode); on the control plane the shared node list with Add node, Retry and Remove (§4.10) | `overview.nodes`; `/api/dashboard/nodes`, `/api/dashboard/verify` |
| `#/config` | Conflict resolution for monitors, groups, channels, maintenance, status pages and tags | each kind's `/conflicts` and `/resolve` |
| `#/accounts`, `#/account` | Accounts on this endpoint, or this dashboard's own accounts on the control plane (admin); your own password, 2FA and sessions | account and auth routes |

Rail badges: open incidents (critical red); active maintenance windows, out-of-view nodes and conflicts (neutral). No other navigation chrome uses status color.

## 4. Screens

### 4.1 Connect and switch endpoint
Unchanged from v1 (see the authentication contract and [browser evidence](auth-ui-validation.md)): password, authenticator code or account token; one node at a time; the credential lives only in the tab's memory; switching remounts every node-bound view so drafts, issued tokens and pending enrollments can't cross nodes.

**Gateway mode (v3.8, not accepted).** `src/gateway.ts` reads `__CANARY_DASHBOARD_GATEWAY__`, which `/canary-config.js` sets before the app starts: `false` in the source copy (`apps/web/public`). The dashboard server's generated script sets it and the control-plane flag to `true`, so the container always shows the control plane below; no current server sets the gateway flag alone, and the gateway-only screens in this list are client groundwork kept with their fixtures, not what the container shows. Only exactly `true` turns it on; a missing or unreadable file means direct mode, unless the dashboard server marked the page as its control plane, described below (Proposed).
- **Sign-in screen:** no node address field. The address is always the page's origin, and one remembered from direct mode is neither read nor overwritten. The copy says to sign in to this dashboard once to see its node and every peered node; second, it says the account lives on the node behind this dashboard and that a sign-in proxy in front of the page doesn't sign anyone in to Uptime-Canary. Fields, method choice and the "Sign in" button are as in direct mode.
- **No switching:** the endpoint button opens **Dashboard sign-in** instead of Switch endpoint: sign in again, or as another account, through the same server, with Sign out or Disconnect. It offers no peer list and no reuse of a token at another address. Its label drops "· switch"; the not-answering banner keeps "Try now" without "Switch endpoint"; the reconnect and renew prompts use the same dialog.
- **Peer addresses are text only:** the connected view's node list carries no peer address, so "Use as endpoint", "View from <peer>" (partition banner and monitor history) and the peer choices in public links and badges disappear. The Nodes page reads the addresses from the overview and labels them "Peer address". Not yet adapted: the monitor history card's empty state still suggests switching the endpoint, and the public page's "another node" field is still offered, though the request it makes is refused (Open).
- **Direct mode** keeps every v1 label and behavior: "Node API address", "Switch endpoint", "Sign in and switch", "Use as endpoint" and the browser proofs that drive them.

**Control plane (v3.9, not accepted).** `controlPlaneMode()` is on when the page carries the dashboard server's marker, exactly `<html data-canary-dashboard="control-plane">`, which the server writes into the page it serves, or when `/canary-config.js` sets `__CANARY_DASHBOARD_CONTROL_PLANE__` to exactly `true`, as the server's runtime script also does. The marker alone is enough, so a missing, blocked or `false` runtime flag can't turn the server's page back into the direct node sign-in; any other marker value counts as none, and without a readable document only the flag counts. It implies gateway mode, so nothing goes to another origin. The dashboard owns the accounts; the layout follows `design/dashboard-onboarding.html`.
- **First owner:** the screen asks the dashboard's own status. On a fresh dashboard it shows "Create the owner account": account name, password (the same 12–128 rule as nodes) with confirmation, and the private setup code, which the server prints in its log at start and keeps in `setup.code` in its identity folder. Creating it signs in at once with an ordinary password sign-in; if another browser created the owner first, the sign-in screen says so. No node address, node account or running node is involved.
- **Sign-in:** "Sign in" with a dashboard account (password, or a token this dashboard issued). The hints say node accounts and a sign-in proxy don't sign in here. If the status can't be read, the screen says so with Try again, and notes that a stopped node never causes it.
- **Selection, not switching:** the top-bar button reads "This dashboard" or "Viewing <label>" and opens **Choose a node**. Choosing keeps the same sign-in and signs nothing out; the view remounts, so polls, catalogs, drafts and late answers from the previous node are dropped. Until the node's first answer, monitoring pages show a "Reading <label> through the dashboard’s server" state, then "Nothing from <label> yet", never an empty "no monitors" list. Without a selection, Overview is the shared node list and other monitoring pages ask to choose a node; Nodes, Accounts and Your account always work. Re-signing in keeps the selection.
- **Requests:** sign-in, account and node-list requests never carry the selection; monitoring requests add `X-Canary-Registered-Node` with the same dashboard credential. A 401 means the dashboard sign-in ended; a selected node refusing the dashboard's credential is the server's 502 and reads as a node problem. Status-page links and badges use `?registration=` on the dashboard's address.

### 4.2 Overview
v1 headline, KPI tiles and matrix, plus: a **Maintenance** tile (active windows and how many monitors they hold), a maintenance tag beside held monitors, and **pending** results in the headline. Latency in cell tooltips says "no measured latency" when a node reports `latencyAvailable: false`; it never shows a measured-looking `0 ms`.

### 4.3 Monitor form
- **Check type** is a grid of native radio cards in eight groups: web and network (HTTP(S), ping, TCP, TLS, DNS, WebSocket, SMTP), remote probes (Globalping, §4.3.1), game servers (Steam game server, §4.3.3), on each node's own system (system service, §4.3.2), databases and caches (PostgreSQL, MySQL, SQL Server, Oracle, MongoDB, Redis), messaging and containers (Docker, MQTT, RabbitMQ, Kafka), infrastructure and RPC (gRPC, SFTP, NTP, SNMP, RADIUS, SIP OPTIONS), and passive/operator (push, manual). Editing collapses the grid to the current type with "Change type".
- **Progressive sections.** Essentials appear inline; credentials, query/assertion, TLS and advanced options sit in disclosures whose closed summary says what's configured. A failed save opens every section with an error. The 16 service protocols are rendered from one declarative field list (`serviceSpecs.tsx`), so labels, hints, bounds and conditional visibility (for example SNMP v3 fields, gRPC unary fields, SFTP host-key pinning) follow the node's contract.
- **Edits preserve what the form doesn't model.** Every option object is edited from a copy of the stored one, so unknown keys survive at every level (including siblings of the protocol object inside `service`, keys inside a stored condition, and unknown channel config and template keys), and an option object whose fields didn't change is sent byte-for-byte as stored (Agreed: unchanged options must not start a new check generation). Changing the type or provider starts from a clean object.
- **Empty can be a value.** Where the node accepts an empty string as meaningful (Kafka's zero-length produce record, RabbitMQ's empty password), the field may be left empty and is sent as `""` rather than omitted; other required credentials stay required.
- **Edit forms load the stored item.** An edit route opened before the overview includes the item shows "not found" and mounts the form only when the item arrives, so its draft and base revision always come from the stored version. The channel form does the same with the channel list (v3.6), so its stored-secret warnings and open sections match the stored channel.
- **Credentials are never blanked by accident.** Stored secrets are prefilled as masked fields with show/hide. PEM "Replace" keeps the stored value until a replacement is pasted ("Keep the stored key" undoes it); only "Remove" clears it. Clearing a stored secret shows "Saving removes the stored value" before save.
- **Schedule and retries:** interval, timeout, retries before down, an optional faster interval while failing, inversion, and active.
- **Ping:** packets per check, payload size, address family; a hint that a node unable to send ICMP reports unknown.
- **Manual:** a segmented status (not set / up / down / pending) and message, explaining that status edits keep the incident.
- **HTTP OAuth2 (protocol 10):** a fourth choice under Authentication, exclusive with Basic, Bearer and an Authorization header. The token endpoint and client ID are required; the client secret key is always sent, and an empty secret is valid. Client authentication is a Basic header (default, explicit `client_secret_basic` is kept if stored) or the form body; scope, audience and a token-endpoint CA are optional. Plain HTTP for the token endpoint or the monitored URL needs the explicit "Allow plain HTTP" opt-in. The secret is masked, previews hide it, and viewers never receive the object.
- **JSONata (protocol 10):** HTTP (under Response content) and MQTT, MongoDB and SNMP (under Query and assertion) take an optional expression, an operator (`==`, `!=`, `>`, `>=`, `<`, `<=`, `contains`) and a typed expected value (text, number, true or false, all available for every operator because the node accepts them; changing the operator never changes the stored type). Pairs that can't pass, such as ordering against true/false, get a warning rather than a save error. It must pass together with every existing matcher. The form never compiles or runs the expression; it states what `$` is for each check, that the node evaluates it in a separate resource-limited worker (a syntax or evaluation error reads exactly like a false result, because the node's diagnostic doesn't distinguish them; MQTT keeps waiting for the next matching message until the deadline; only an unavailable worker reports pending), the comparison rules, and the known differences of the Go port from the JavaScript JSONata Uptime Kuma uses. Unknown keys in a stored condition survive edits. Viewers don't receive HTTP JSONata.
- **Push:** a 64-hex token generated in the browser from 32 CSPRNG bytes, show/copy, **Rotate token** with a warning that it starts a new check, opt-in GET acceptance with a caution about URL logging, and a `curl` example (token masked unless shown). On the control plane with a node selected, the example targets the dashboard's address with that registration (`POST /api/push?registration=<id>` with `Authorization: Push <token>`, or the GET form), names the node, says the server forwards the push token but never a sign-in or cookie, and says the sender must reach the dashboard and pass any sign-in proxy, or send without `registration` straight to the node on a private network (decision 63). In direct mode, or with no node selected, the example is byte for byte the earlier one.
- **Alerts:** a channel picker (provider, recipient count, disabled/conflict flags, unknown IDs kept visible), the legacy webhook in a disclosure, and repeat while down.
- **Organize:** tags with optional value and a per-assignment "Public" flag; group.
- **Check-generation warning.** The form mirrors the node's `sameCheck`. If the edit changes what is checked and the monitor has an open incident, a warning above Save names the changed fields and says the incident closes without a recovery alert (resolves v1 open question 11).
- **JSON (advanced)** previews the exact request body (credentials masked unless shown), copies it, and can fill the form from a CLI/API object. It complements the fields; it doesn't replace them.

#### 4.3.1 Globalping (protocol 12)
The type picker gains a **Remote probes (third party)** category with one entry. The section opens with a note on what leaves the nodes (target, location and, for HTTP, path, query and headers including Authorization go to Globalping and its probe; the token and API CA stay), then **Measurement** (Ping, HTTP, DNS), the mode's own target (URL, host or name, each kept while switching modes) and **Probe location** with magic examples and the reminder that the dashboard doesn't verify where a probe is.
- **Ping:** packets (1–16, empty 3), ICMP or TCP, and a TCP port (empty 80) shown only for TCP.
- **HTTP:** GET, HEAD or OPTIONS (no body), HTTP/2 (https only), skip TLS verification (danger, https only), a **Request headers** disclosure (32 headers, 32 KiB, no Host/User-Agent, Authorization as the only target auth) and **Response conditions** (status ranges, a literal case-sensitive keyword with "Fail when found", and JSONata on the strict-JSON remote body, with the 10 kB/truncation caveat). HEAD with a body condition saves with a warning that it can never pass.
- **DNS:** the 16 record types the schema allows, UDP or TCP, a resolver host or IP without a port, port (empty 53), an RE2 answer pattern matched per answer value, and "Accept an empty answer".
- **Globalping API and failures** (disclosure): masked token, API address (empty = public API; path prefix without `/v1/measurements`), "Allow plain HTTP for the API" (danger), extra API CA certificates (API only, not the target) and "Treat Globalping failures as down" with the pending-by-default explanation.
- **Probe timeout** (5–30 s) and **IP version** (refused for IP targets), then a timing and quota note computed from the form: the check timeout covers create, probe and polling; when it's shorter than probe + 10 s a one-click "Use N s" is offered; it states measurements per hour across the chosen nodes and warns below a one-minute interval.
Edits start from the stored object: unchanged spellings (`icmp`, `head`), unknown keys and the token survive, and exactly one mode object is sent (`{}` for defaults). The change warning compares `globalping` the way the node does (Go `omitempty` JSON), so a rename never warns and a location change does. Viewers get "Hidden from viewers" facts and the node's `scheme://host/` target. The JSON preview masks the token and header values.

#### 4.3.2 System service (protocol 16, development; local Windows and hosted CI evidence)
The type picker gains an **On each node's own system** category with one entry, **System service** (type `system-service`). Its only setting is the target, labelled **Internal service name** (examples `sshd.service`, `Spooler`); there is no options object and no credential field, and the shared schedule, retries, retry interval, inversion, placement, alerts, groups and tags apply unchanged.
- **Name rule.** The form mirrors the node exactly, never stricter: 1–256 ASCII characters, a letter, digit or underscore first, then also `.`, `-` and `@`. Each error names the first problem: spaces (with the display-name hint "Spooler, not Print Spooler"), non-ASCII, a path, a pattern, quotes, a leading dash, dot or `@`, another character, or length. Surrounding spaces are trimmed like other typed targets.
- **Where it runs.** Under a valid name a line shows what each platform reads: Linux nodes ask systemd about the unit with `.service` appended when it's absent (case-sensitive, like the node), Windows nodes ask the Service Control Manager for the name as typed. A note then says that each selected node checks its own operating system, never another host; that the query only reads state, with no credentials; how up, down and pending are decided; and that a node in an ordinary container, such as the Alpine image, can't see the host's systemd or Windows services and stays pending. It recommends running the node on each machine to be watched and never suggests mounts or privileges. The placement hint changes to the same idea, latency is stated as unmeasured (a dash), and a 5 s timeout is suggested in words; the 10 s form default isn't changed silently.
- **Results.** Running (systemd: active) is up; stopped or not installed is down; an unreadable manager (none, no permission, an unsupported OS, busy check workers, or no answer within the check's timeout) is pending, which never recovers an outage.
- **Generations.** `type` and `target` compare exactly as stored, as the node's `sameCheck` does, so `sshd` → `sshd.service` starts a new check even though Linux reads the same unit. The warning calls the target "service name" for this type.
- **Detail, conflicts, edits.** Details show **Read from** (both platform names), **Up when**, **Down when**, **Pending when** and **Latency**; viewers see the same, since a service name isn't a secret. The location summary speaks of machines rather than network paths (failing on one node and passing on another means the service differs between them). The conflict resolver's check row adds "read by each node from its own operating system"; unknown future fields stay in its "Other fields" row. Edits start from the stored monitor, so a rename or pause sends the stored name and every unknown field unchanged.

#### 4.3.3 Steam game server (protocol 17, development, local Windows evidence only)
The type picker gains a **Game servers** category, after remote probes, with one entry: **Steam game server** (type `steam`, hint "Listed in Steam's server directory"). The section is structured fields over the node's `steam` object, never the generic service form, in this order:
- **What is shared, first.** A note (`.steam-note`, role `note`) says that each check tells the Steam API which server is watched and sends the API key with it: every selected node resolves the host (IPv4 first) and makes its own request with the resolved address and port and the key, which travels as a URL query parameter; only Steam's API or an HTTPS endpoint or proxy the operator trusts should be used, since whoever runs it can read the key; and the check reads the server's listing in Steam's directory, never the game's own protocol.
- **Server address** (`host:port` or `[IPv6]:port`). The rule mirrors the node without being stricter: Go's `SplitHostPort`, an ASCII host name or IP (the ICMP target rule, punycode for other scripts), no IPv6 zone, a decimal port 1–65535 without leading zeros, at most 320 characters. The hint says to use the port Steam's server list shows, which for some games is a query port. It isn't one of the typed-target types: the Steam section owns the field, as Globalping does.
- **Steam Web API key** (required masked secret field; 1–256 printable ASCII characters without whitespace; pasted surrounding whitespace is trimmed). Changing a stored key shows an inline warning that a new check generation starts, with **Keep the current key**.
- **If the Steam API fails**: a two-way choice, **Pending (recommended)** or **Down**. The hint explains attribution: an unreachable or timed-out API, an error status (rate limits and refused keys included), a redirect or an unreadable answer says nothing about the server; Down follows Uptime Kuma but alerts for faults that may be Steam's, the key's or a proxy's. A check the node cancels stays pending either way; a missing listing and an unresolvable host are always down.
- **Measure ICMP latency after a positive listing** (on by default; off stores `skipLatency: true`) and **ICMP payload size** (optional, 0–65,500; empty omits the field for 32 bytes, and 0 is kept as a zero payload). The hint says the echo is the only latency, that a lost reply or missing ICMP permission shows a dash without changing the listed result, and that the API's response time is never latency.
- **Steam API endpoint** disclosure: **API address** (optional; https://, or http:// only with **Allow plain HTTP for the API**; host, optional port and a clean path prefix, without credentials, query, fragment, a dangling colon, `%`-escapes Go wouldn't write itself, or empty, `.` and `..` segments; the node appends `/IGameServersService/GetServerList/v1/` to whatever prefix is given, so a clean prefix that already ends in that path is valid too; the node admits it, and the form accepts it and keeps it exactly as stored) and **Extra CA certificates for the API** (PEM certificate blocks only, up to 128 KiB of raw bytes, checked before anything else; added to the system roots for the API's HTTPS connection only; a note says they aren't used while the address is plain http://). Blank and the space between certificates follow Go's `bytes.TrimSpace`, the Unicode White_Space property, not JavaScript's `trim`: NEL counts as whitespace and a BOM doesn't. An unedited stored value, whitespace-only included, is sent byte for byte; only an edited value that is all whitespace is omitted. There is no switch to skip verification.
- **Timing and quota** (`.steam-timing`): the timeout covers resolving the host, the API request and the echo; calls a day across the chosen nodes; a warning above the 100,000 calls a day Steam's Web API terms allow per key. The placement hint says every node calls the API with the key, and that more nodes separate a node's own DNS or API path, not the route to the game server.
Edits build on the stored object: unknown keys survive, false and empty `omitempty` fields are omitted on edited values, and an unedited object is sent exactly as stored. The change warning compares `steam` the way the node's `equalJSON` does (the key always encoded, `packetSize` a pointer, so 0 differs from absent) and names "Steam API key or options" and "server address". **The key never appears outside its own field**: the JSON preview masks it even when credentials are shown (and says so), detail facts say "set · always hidden" even when secrets are revealed, and the conflict resolver masks it in both its views. Details show **Steam directory** (the address, IPv4-first resolution, "a directory listing, not a game-protocol query"), **Up when**, **Down when**, **If the Steam API fails**, **ICMP latency** (payload size, or skipped), **Steam API** (masked address unless revealed, plain HTTP and CA counts), **API key** and **Sent to the API**. Viewers receive no `steam` object and see the address, the membership and latency rules and "API, key and options: Hidden from viewers". The location summary explains that every node asks the same directory, so a split points to differing DNS answers or, with the opt-in, API reachability. The conflict resolver's check row adds "Steam directory listing", the latency mode, the opt-in and "API key hidden".

#### 4.3.4 PM2 process (protocol 18, in progress; not accepted)
The **On each node's own system** category gains a second entry after System service: **PM2 process** (type `pm2`, hint "Named process online in the local PM2"). The section is structured fields over the node's `pm2` object, never the generic service form, in this order:
- **Where it runs and what it may touch, first.** A note (`.pm2-note`, role `note`, styled like `.svc-note`) says that each selected node asks the PM2 daemon on its own machine, never another host's; that it connects to an already running daemon as the account Canary runs under and only reads the process list (no daemon start, no process start, stop or restart); that only PM2 6.0.8 is read and another version stays pending; that access to the daemon's socket is a deployment step which lets anything running as that account control PM2 fully, even through a read-only mount; and that a containerized node gets no access to the host's PM2 automatically but needs explicitly provisioned access to the intended daemon's socket, with the same account rule applied to the daemon's user ID as mapped into the container. It says nothing about the wire protocol, and the form has no privilege, user, shell or command settings.
- **Process name** (the monitor's target). The rule mirrors the node's exact-text check without being stricter: 1–256 UTF-8 bytes, valid Unicode, no control characters (Go's `unicode.IsControl`), no Unicode White_Space at either end (Go's `strings.TrimSpace`); inner spaces and any punctuation are literal. It is never trimmed: a pasted surrounding space is an error, not silently removed. The hint says case, internal spaces and punctuation count, that a number is a name (`3` is a process named "3", never PM2 id 3 or a PID) and that cluster instances with the name all count. It isn't a typed-target type: the PM2 section owns the field, as Steam does.
- **Daemon connection**: a two-way choice, **Unix socket (Linux)** or **Windows named pipe**, stored as `transport`. Each hint says the other platform needs a separate monitor. The socket's hint says the node asks only a daemon whose effective user ID is Canary's own, so a daemon run by another account stays pending even when its socket is reachable. The pipe's hint states the Windows deployment prerequisite in plain words: a daemon already running as Canary's own account, and from the pipe's first creation only Canary's account, SYSTEM and Administrators able to create instances of it or change its security (who could serve or reconfigure the pipe, not which clients connect); the node is pending when the daemon's account or the pipe's present owner and permissions don't fit, but it can't see their history, so tightening a pipe that was once more open isn't enough. It names no system calls, security masks or bypass setting. A connection this dashboard doesn't know is sent only on a monitor already stored with it: the warning then says it's kept as stored with the settings that came with it, and choosing a known connection drops those settings (the node refuses keys it doesn't know). An unknown connection typed or imported over anything else gets a different warning (it can't be saved) and a **Daemon connection** field error.
- **PM2 home** (Unix only; hidden for the pipe). A new monitor starts blank: the form never guesses a user's home or reads the environment. The hint says that on a node in a container this is the path where the daemon's home is mounted inside the container. The rule mirrors the node: one clean absolute POSIX path (Go's `path.Clean` leaves it unchanged, so no trailing slash or empty, `.` or `..` segment), no backslash, `~` or `$` anywhere (nothing is expanded), the exact-text rule, and `path.Join(home, "rpc.sock")` within 107 bytes, so at most 98 bytes for any home but `/`. Under a valid home the hint shows the socket path every chosen node opens. Switching to the pipe keeps the typed home in the draft (switching back restores it) but never sends it, because the node refuses any `home` with the pipe.
- **Namespace** (optional): empty omits the field, since the node refuses an explicit empty one, and matches the name in every namespace; otherwise the same exact-text rule, case-sensitive.
- **Timing**: latency isn't measured (a dash); the timeout guidance is neutral (cover how long each node's PM2 can take to answer; no answer in time is pending), with no suggested value and no change to the field; a restart passes through stopping and launching, which count as down, so retries are the remedy. The placement hint says each chosen node asks its own daemon through the same connection and home, and that mixed Linux and Windows machines need separate monitors.
Edits build on the stored object, so key order and keys from a newer node survive, and an unedited object is sent exactly as stored. The change warning compares `pm2` the way the node's `equalJSON` does (`transport` always encoded, empty `home` and `namespace` absent) and names "process name" and "PM2 connection, home or namespace". **The PM2 home is private configuration, not a secret**: the masked JSON preview and the conflict resolver's masked view replace it with the mask (unknown credential-named keys too), and "Show credentials" or the resolver's reveal shows the authorized value; the process name and namespace stay visible to editors as identifiers, with no claim of generic secret detection. "Fill the form from JSON" refuses a masked copy (`pm2.home` names the placeholder) and fills the PM2 fields from a revealed one. Details show **Read from** (the exact name and the namespace or "any namespace"), **Connection** (socket in the PM2 home, hidden until revealed, or the named pipe, each with its account rule), **Up when**, **Down when** (stopped, stopping, launching, errored, waiting to restart or `one-launch-status`, the six states the node counts as down, or no such process in the chosen namespace, or in any namespace when none is set), **Pending when** (no definite answer, each cause named: no daemon, another account or an unfitting Windows pipe, no permission, a connection or operating system the node doesn't support, with macOS and other Unix systems always pending, another PM2 version, an unreadable answer, an unknown state, busy or failing check workers, no answer in time; a definite down outweighing an unknown sibling, never inverted, never recovering an outage) and **Latency**. The location summary's pending line names the same causes. Viewers receive no `pm2` object and see the name, the rules and "Connection and namespace: Hidden from viewers". The location summary speaks of machines, as for system services. The conflict resolver's check row adds "read by each node from its own PM2 daemon", the connection and the namespace (in monospace, wrapping anywhere).

### 4.4 Monitor detail
v1 location table and incidents, plus: certificate verification and validity per location, consecutive failures, a **Manual status** card for editors, and **History** with a range control (1 h, 6 h, 24 h, 7 d, 30 d, 90 d, custom from/to) and a check limit (100/300/1,000).

**Observed time** (protocol 11) comes first in the card: three tiles (observed availability with "up X of Y known", coverage with known, unknown and pending durations, and down time with any maintenance overlap), a 100 % column chart per bucket and a note. Presets end at the node's clock from its latest overview, because the node rejects a future end; a custom end in the future is clipped and says so. Buckets default to the smallest of 1 min … 1 d that keeps about 120 columns, and the **Buckets** menu offers every size that stays within the node's 4,096 buckets; ranges longer than 90 days are explained instead of sent. Percentages are the node's own, truncated (99.9996 shows 99.999 %, never 100 %), a tiny share shows "<0.01 %", and no known time shows a dash. The note names the node, the exact window, `retainedFrom` (or that nothing is retained yet and old checks aren't converted), the 90-day and 100,000-span limits, and that it isn't an SLA. Nodes before protocol 11 get a one-line note instead.

Under **Individual checks**, statistics tiles show samples by state, **sample availability** with its numerator and denominator (up ÷ (up + down), pending/unknown excluded) and P50/P95 latency with `latencyCount` as its denominator. A note says it is a sample ratio from one node, not a time-weighted uptime or SLA, and states the node's retention. The latency line skips unmeasured samples. Details list every type's options (credentials masked, "Reveal credentials" for editors, "Hidden from viewers" for viewers), channels, tags and, for push, when the heartbeat deadline started counting. A **Delivery attempts** card shows this monitor's per-destination outcomes.

### 4.5 Groups
v1, with wording updated for channels: holding is per destination; destinations the outage monitor doesn't reach fail open after the grace period.

Protocol 11 adds **nesting**. Without a search, groups render as a tree (children indented under a rule); a search shows a flat list so no match hides inside a parent. Each card shows the path ("In Site › Rack"), a **Health** chip beside the dependency chip, a health bar and counts (up, down, pending, unknown, plus paused and in-maintenance when nonzero) with "n active monitors across this group and m nested groups. Current results, not uptime.", the parent, and nested groups with their health glyphs. An empty or all-paused group says it is pending rather than up. When the node can't evaluate the hierarchy the card shows Unknown with the node's reason and no counts; a missing parent or cycle is named on the card.

The form adds **Parent group** (optional): every group by path, minus the group itself and its nested groups; conflicted groups and groups whose own parent chain is broken are listed but disabled with the reason. The hint says nesting organizes health only. A stored parent that has gone missing or into a cycle blocks saving with a field error until another parent or the top level is chosen, because the node validates the whole chain on every save. Edits start from the stored group, so unknown fields survive; "None · top level" omits `parentId`. Monitor and maintenance pickers label groups by path, and the maintenance hint says nested groups aren't included.

- **Channels** list provider, masked route, recipients (email only), usage and revision with Test, Edit and Delete. Chat and push routes show the API origin and non-secret options only, never a token, topic, chat ID or user key. - **Delivery attempts** table: last attempt, event (kind, monitor, incident), destination (channel and destination ID), outcome chip with HTTP status, next retry and hashed acknowledgement, node and failures. - **Receipts** keep the v1 ledger; duplicates are now per destination.

### 4.7 Maintenance
Cards sorted conflict → active → scheduled → ended, each with a status chip ("Active · holding alerts", "Scheduled", "Disabled", "Conflict · not applied"), a schedule sentence in the schedule's own named zone, the node's current window and next start **in explicit UTC plus the viewer's local time and a relative time**, the selection, the node's reason, and which monitors it holds now. ### 4.8 Status pages and the public route

- **Badges:** the Share dialog and the editor's Share card list badge addresses for the saved page when it is published (drafts say "Publish the page to get badge links"): the whole page, then each service whose public section ID and public name match exactly one entry, each with a live 20 px preview and Markdown, HTML (whole page) and image-URL copy buttons. **Served by** chooses the node address; loopback, private and plain-HTTP addresses get a caveat. - **Public page** (`#/status/<slug>?node=…`): page title and description, an overall state panel ("All systems operational", "n of m services down", "Checks in progress", "Status partly unknown"), maintenance stated beside results, pinned announcements first, sections with state chips, monitor rows with tags and certificate validity, then, only when the node returned a published `availability` field, a separate **Last 24 h** line under the current state: availability and coverage (truncated basis points from the millisecond totals, like the badge), "observed by this node, as of" the window end, a compact hourly strip (up, down and pending fill from the bottom; the rest is hatched unknown; a top mark for maintenance; tooltips) and an **Hourly figures** table. Not found, unreachable and stale data each have their own message; the last good page stays visible, marked, when a refresh fails for the same node and page, while "not found" (an unpublished or withdrawn page) clears it. A late answer from a node or page no longer selected is discarded. Nothing switches nodes automatically.

Color is decoration: the name always sits beside it, and only strict `#rrggbb` values reach a style attribute.

### 4.10 Nodes, Configuration, Accounts
**Control plane (v3.9, not accepted).** Nodes is the dashboard's shared list, the same for every account: the path "This browser tab → This dashboard → Each node’s private address", summary chips, and one card per node with its state (Answering, Starting, Not answering hatched, Credential refused and Different node at this address with a serious edge, Being added for the bundled node, Enrollment unfinished, Removal unfinished), last read, monitor count, Open, and Check now. Administrators also see addresses, **Add node**, Retry for unfinished work and Remove; the bundled local node is tagged "Added automatically" and can't be removed here. Viewers and editors see the list read-only without addresses. Add node verifies first (label, the address as the dashboard's server reaches it, an enrollment credential), shows the node ID the server proved, the ticket's remaining time and a plain-HTTP warning, and adds only on confirmation. The credential is cleared after every verification attempt, on Back and on close; an unused ticket is discarded on Back and on close. Removing explains whether the node confirmed revocation (204) or the entry stays as Removal unfinished (202). Accounts and Your account manage this dashboard's accounts, with dashboard role descriptions. With a node selected, Nodes also lists the peers that node reports and whether each was added.

Nodes and Accounts are unchanged in direct mode. In gateway-only mode (no current server; §4.1) the Nodes path reads "This browser tab → Dashboard server (its origin) → <endpoint> (address set on the server) ⇄ peers", the endpoint card is "Reached through" the dashboard's origin and tagged "Dashboard’s node", and the accounts note says the dashboard signs in with an account on that node, which shows its peers without an account on each. Configuration resolves conflicts for all six resource kinds; the monitor resolver binds type, target and every option object into one "Check" row so an invalid combination can't be picked, and shows option JSON masked unless credentials are revealed.

## 5. Primary workflows

**W1 · Triage: the service or the path?** Headline → matrix row (which columns are red) → chip (*everywhere* or *n of m*) → monitor detail sentence → history on a node that runs it.

**W2 · Operating through a partition.** The banner names the out-of-view peers and explains independent monitoring and possible duplicates. Out-of-view cells are hatched; chips say "n not in view". "View from <peer>" opens the switch dialog with that peer's address (direct mode only; on the dashboard server the browser has no route to the peer, and an administrator registers the peer to make it selectable).

**W3 · Explaining a duplicate.** Receipts → Duplicates filter, or the incident's "1 duplicate" tag (counted per destination); the Notifications cards explain why.

**W4 · Resolving a conflict.** Rail badge or "conflict" link → Configuration → pick per field or a whole version → preview → Save resolution (names all heads) → 409 means review again. Works for monitors, groups, channels, maintenance, status pages and tags.

**W5 · Adding a monitor.** Pick a type; fill the essentials; open sections only as needed; watch the notification order; create; land on the detail page with the acknowledged revision.

**W6 · Losing the endpoint.** The top bar switches to "Not answering · data from 1 min ago", a banner explains the last data is shown, the views dim, and polling backs off (5, 10, 20, 30 s). "Try now" and, in direct mode, "Switch endpoint" are offered; nothing switches automatically. On the control plane, a selected node the server can't reach, or that refuses the dashboard's credential, is the server's 502 or 504 with a fixed node message: it reads as that node's problem, the dashboard sign-in stays, its Nodes card shows the state, and the other nodes and the dashboard's own pages keep working. A dashboard server that doesn't answer at all reads "Cannot reach this dashboard’s server" with the sign-in proxy hint. (The gateway-only wording, for a server that had no node set, applied to the replaced one-node container.) A 401 stops polling and offers sign-in.

**W7 · Accounts across nodes.** Create the account with a generated token on one node, copy it, switch to another node and create the same account with "Use a token I already have". This needs direct mode or the CLI. On the control plane it isn't needed: one dashboard account reaches every registered node, and node accounts aren't copied into the dashboard.

**W8 · Read-only wall display.** A viewer sees every view except Accounts; actions become lock tags; credentials and channel configuration show "Hidden from viewers". Phones collapse healthy rows.

**W9 · One alert for a shared outage.** Create a group for the place or dependency; pick its outage monitor (with the same channels as its dependents) and grace period; add dependent monitors to the group from their forms. During an outage the dependency's alert is sent, dependents show "alerts held" with the reason for destinations it reached, and incidents keep recording.


**W10 · Email the on-call team.** Notifications → New channel → SMTP/Mailgun/Brevo/Mailchimp → sender and recipients → Create → Test → Delivery attempts shows each recipient's outcome → pick the channel in monitors. *Chat or push (protocol 13, in progress):* the same flow with Slack, Telegram, ntfy, Gotify or Pushover; the channel is one destination.

**W11 · Plan maintenance.** Maintenance → New window → choose monitors or groups → strategy and zone → Schedule → the card shows the node's next window in UTC and local time → during the window, monitors show the maintenance tag and attempts show "Held".

**W12 · Publish a status page.** Status pages → New → title → sections → pick monitors and type public names → opt into certificate dates or public tags → Published → Create → Public link → copy for visitors.

**W13 · Monitor a cron job.** New monitor → Push → copy the generated token or the `curl` example into the job → Create. A missed heartbeat fails like any other check.

**W14 · Read history honestly.** Monitor → History → pick a range → read observed time (availability of known time, coverage, down time; unknown gaps hatched) → then samples by state, sample availability with its denominator and latency with its sample count; each note says what it isn't.

**W15 · Organize groups.** Groups → New group (or Edit) → Parent group → Save → the tree shows the group under its parent, and the parent's health counts include it. Moving it to "None · top level" removes the link. Nothing about alerts or maintenance changes.

**W16 · Share a badge.** Status pages → Share (or the editor's Share card) → choose the serving node → copy Markdown for the whole page or one service → paste into a README.

**W17 · Set up a dashboard and add a node (control plane, in progress).** Open the dashboard → Create the owner account (name, a 12–128 character password, the setup code from the server's log or `/identity/setup.code`) → signed in, with no node needed → Nodes: the bundled node, if configured, appears as being added, then starting, then answering → Add node → label, the address the dashboard's server reaches, an admin credential for that node → Verify → check the node ID the server proved → Add → Open the node, with the same sign-in. An administrator then creates editor and viewer accounts on Accounts. The node's admin token stays an enrollment credential, never the dashboard password (Proposed; layout in `design/dashboard-onboarding.html`).

## 9. Data honesty and security
- **One endpoint, named everywhere.** Views say "as known to <id>"; nothing aggregates across nodes.
- **Polling:** `GET /api/overview` every 5 s, one request at a time (a refresh during a request is queued, never overlapped), paused while the tab is hidden, aborted on switch or disconnect. Writes trigger an immediate refresh. History refreshes every 15 s while its card is open.
- **Stale and rejected:** on failure the last overview stays visible, dimmed, with its age; retries back off to 30 s. A 401 stops polling. No placeholder or sample data is ever shown as live.
- **Acknowledged writes only:** buttons read "Saving to canary-a…" until the node answers; confirmations quote the returned revision. 400/403/404/409 keep the user's input and show the node's reason.
- **Tokens:** kept only inside the in-memory API client. Never in `localStorage`, `sessionStorage`, cookies or URLs; disconnect and reload drop it. Only the last endpoint address (direct mode only) and the theme preference are stored. Requests use `Authorization: Bearer`, `redirect: 'error'`, `credentials: 'same-origin'`, `no-referrer` and a 15 s timeout.
- **Gateway mode stays on its origin:** `request()` in `api.ts`, the only place the dashboard opens a request, refuses any origin other than the page's before anything is sent, with an `OriginRefused` error naming both origins: a peer's address, a typed or linked node address (including `node` parameters in older status-page links) or an old remembered one. It never re-aims such an address at the page's origin, because a link's address names a particular node, and the gateway's node could answer differently. A gateway page without an `http(s)` origin contacts nothing. The server takes no identity from the browser or a proxy: the Canary bearer is still required, and the dashboard server sends a node no browser cookie, bearer or origin, only the role credential it saved for that node (Proposed).
- **Node credentials stay on the server (control plane).** The browser sends only the dashboard sign-in and, on monitoring routes, a registration ID; the server picks the saved address and the node credential for the account's dashboard role, so a viewer reaches the node as that node's viewer account and the node's own redaction applies. An enrollment credential typed into Add node goes once to the server and is cleared from the form after each attempt; saved node credentials never reach the browser (Agreed, from the [contract](dashboard-control-plane.md)).
- **Sign-in proxies:** `same-origin` credentials let an authenticating reverse proxy in front of the dashboard see its own session cookie. With the container, the proxy routes the whole origin to the dashboard server, which reaches the registered nodes itself; in direct mode it can instead serve the dashboard and a node's `/api/` on one origin. The dashboard never reads or sets that cookie, and the server never passes it on, so a dashboard sign-in (or, in direct mode, the node's) is still required. Browsers attach no cookies to a node on another origin, so in direct mode a node behind such a proxy is usable only from the dashboard on its origin. Redirects stay refused: when the proxy session ends, requests fail, and at that origin the message names an ended proxy session as one possible cause and asks for a full page reload, which goes through the proxy's sign-in and drops the tab's in-memory credential (Proposed).
- **Untrusted strings** (names, targets, messages, reasons) render as React text; tooltips use text only.
- **Webhooks** are masked to their origin by default (paths and queries often hold secrets); viewers never receive them.
- **Stored credentials** (service passwords, DSNs, PEM keys, channel API keys, push tokens) reach editors and admins only, masked until shown. Viewers receive configuration with these removed by the node and see "Hidden from viewers".
- **Async completions are bound to their connection.** Every write checks that the tab is still on the same connection before publishing its result, so a slow answer from one node can't appear on another.
- **The public route** reads `GET /public/status/<slug>` with no `Authorization` header, even while signed in; like every request it sends cookies only to the dashboard's own origin (a sign-in proxy's), never to another node address. It renders the response as text after keeping only expected fields. Tag colors must be strict `#rrggbb`. The link carries public node addresses only; on the control plane links and badges use the dashboard's own address with `?registration=<id>`, a public selector, and the server reads the page from that saved node without any management credential.
- **Channel tests** send real messages, so they always ask first; saving a channel sends nothing.

## 11. Choices made here (reversible)
v1 choices 1–14 still hold. New in v2:

15. Service protocols are described declaratively; edits start from a copy of the stored object and unchanged objects are resent byte-for-byte.
16. Secrets are prefilled masked for editors (the API returns them to editors), with explicit removal warnings instead of write-only fields.
17. Push tokens are generated in the browser (32 CSPRNG bytes) and never leave the form except in the save request and on explicit copy.
18. Duplicate receipts are counted per destination (`incident · kind · destination`).
19. Maintenance windows are shown as the node computed them, in UTC and local time; the dashboard never re-implements the DST engine.
20. Public pages require a typed public name per monitor; private names are published only by an explicit button.
21. The public route renders outside the signed-in shell and never sends the management credential, even while signed in.
22. Tag colors are validated to `#rrggbb` before styling and always paired with the tag name.

New in v3:

23. Observed-time presets end at the node's last reported clock rather than the browser's, so a request never names a future instant.
24. Observed and sample availability stay separate figures with different scales; neither is averaged into the other.
25. The conflict resolver owns its fields per row and carries any field no row knows (from a newer node) as an "Other fields" row, so a resolution never drops data.
26. Badge links come only from the saved, published page; the dashboard never advertises a link the node would answer with 404.
27. A badge image names one serving node and never a credential; there's no cache-busting parameter, because the node accepts exactly `group` and `monitor`.
28. The public page renders badge previews only while a visitor opens the embed panel, so nobody's browser fetches images they didn't ask for.

New in v3.1:

29. Globalping is its own "Remote probes (third party)" category, and its privacy note is the first thing in the section, before any field.
30. Provider failures default to pending in the copy and the facts; "down" for them is an explicit, explained opt-in.
31. The timeout recommendation (probe + 10 s) is offered, never applied silently; shorter timeouts save with a warning.
32. URL and API checks follow the node's raw parsing, not the browser's: international host names must be punycode, and `..` path segments are refused rather than resolved.

New in v3.3 (protocol 15, development):

33. Published history sits under a service's current state as its own line, never in the state chip, so past up time can't read as present health.
34. The public figures are truncated basis points from the node's millisecond totals, matching the badge; the node's floats are only checked for consistency.
35. A published field that is unavailable, or in any way inconsistent, draws no figures at all; there is no partial or healthy fallback.
36. The strip legend appears once per page, under the first strip; every strip's exact values are in its hourly table.

New in v3.4 (protocol 16, development):

37. System service has its own "On each node's own system" category, beside remote probes, so where the check runs is the first thing the picker says.
38. The container limitation is stated as a fact with one remedy (run the node on the machine to be watched); the dashboard never suggests host mounts, sockets or extra privileges.
39. The 5 s timeout is a suggestion in the copy; switching to this type doesn't change the timeout field.

New in v3.5 (protocol 17, development):

40. Steam gets a "Game servers" category rather than joining remote probes: it reads a third-party directory, not a probe's measurement, and the label is where an operator looks for it.
41. The Steam API key is masked even in the revealed JSON preview and revealed details, a stricter rule than for other credentials, because the node must send it in a URL query string; it is visible only in its own masked field. Copying the revealed preview therefore doesn't carry the key, and the preview says so.
42. The failure policy is a visible two-way choice, not a checkbox inside the endpoint disclosure, because it decides whether provider faults alert.
43. The payload size stays visible and kept while latency is skipped, so switching measurement off and on never loses a stored size, including 0.

New in v3.6 (2026-10-24 review fixes, PR #6):

44. "Fill the form from JSON" refuses any value that still holds the mask (`•••`) and names where it is, so a masked copy can't be saved with the placeholder as the real token, password, header or body. For the Steam key, which is always masked, it says to remove `apiKey` and enter the key in its own field.
45. An untouched Mailgun region is sent as stored: a channel saved without one stays without one, because the node keys each recipient's destination on the raw value.

New in v3.7 (protocol 18, in progress; not accepted):

46. PM2 joins "On each node's own system" beside System service rather than getting its own category: both read only the node's own machine, and the picker says so first.
47. The connection is a visible two-way choice and the home field disappears for the Windows pipe, so the form can't send a combination the node refuses; the hidden home stays in the draft so switching back loses nothing.
48. The process name is never trimmed, unlike other typed targets: PM2 names are matched exactly, so a surrounding space is reported instead of silently changing which process is watched.
49. The PM2 home is masked in the default JSON preview and conflict view but shown on reveal, like a proxy URL rather than the Steam key: it locates a privileged socket but isn't a credential.
50. A connection this dashboard doesn't know survives only where a newer node stored it, with its other keys, so an unedited save changes nothing; it isn't a way to send a new value. Typed or imported over anything else it is a field error, and replacing it with a known connection drops the keys that came with it rather than sending keys the node refuses.

New in v3.8 (dashboard gateway mode; not accepted):

51. The mode is a small run-time file, `/canary-config.js`, not a build flag, so one bundle serves the container (now the control plane, decision 61) and the development server or other static hosting (direct). Only exactly `true` turns it on. A missing or broken file therefore falls back to direct mode, whose sign-in screen visibly asks for a node address instead of failing silently.
52. Another origin is refused with a message, not re-aimed at the page's origin: an address in a link or memory names a particular node, and silently asking the gateway's node instead could show a different node's answer under it.
53. Gateway mode drops peer addresses from the connected view's node list in one place, so every action that would contact a peer (switching, "View from", public-link and badge node choices) disappears together and later views inherit it; the Nodes page shows the addresses as text from the overview.
54. Behind a gateway the endpoint button opens "Dashboard sign-in" rather than disappearing: the path, the account in use and sign-out stay one click away, and signing in as another account still works through the same server.
55. Signing in to a proxy in front of the dashboard signs no one in to Uptime-Canary, and the sign-in screen says so: there is no account replication or header-based sign-in, only the entry node's own accounts (gateway-only; on the control plane the accounts are the dashboard's own, decisions 56–62, and the same rule about proxies holds).

New in v3.9 (dashboard control plane; not accepted):

56. The control plane is its own flag beside the gateway flag and implies it, so a server that sets only the new flag still keeps every request on its origin; gateway-only and direct deployments keep their screens and fixtures.
57. A selection is a header on monitoring routes only, applied inside the API client, so identity and account calls stay with the dashboard whichever node is shown, and the existing monitoring views are reused unchanged.
58. Selecting a node replaces the connection identity instead of patching it: everything node-bound remounts, exactly as switching endpoints did, but the credential is carried over, so nothing is signed out.
59. Monitoring pages wait for a selected node's first answer instead of rendering its empty stand-in, because an empty list would read as "this node has no monitors".
60. No node selection is stored between visits. Selecting is one click on the Overview, and nothing about a node choice is kept in the browser.
61. The dashboard server also marks the page it serves, and that marker alone turns the control plane on. A separate runtime script can be blocked, cached or left out by a proxy in front of the page, and falling back to direct mode there would ask for a node address the browser must never contact; the marker comes with the page itself. Decision 51's direct-mode fallback still applies wherever no server marks the page (development server, static hosting).
62. Gateway-only stays a client mode with its fixtures, but no container ships it: the one-entry-node container it was written for was replaced by the dashboard server before it was validated, and that server always sets both flags and the marker. The control plane builds on the same origin rules, so keeping the gateway-only path costs only its screens and fixtures.
63. Push senders are machines holding only a monitor's push token, so the dashboard's push route takes that Push credential and no dashboard sign-in. The node is chosen by the `registration` query, which the server removes before the node sees the request; the node's own token, rate and durability checks still decide, and no dashboard credential or proxy cookie is forwarded. A front proxy still guards the route: the copy points senders to the node's private address rather than to an `/api/` exemption.

## 12. Open questions
1. **Outage policy.** Keep "any location", or add threshold/all policies per monitor?
2. **Merged history.** Fetch history from every node for multi-location charts (needs cross-node auth and CORS), or keep endpoint-only history with switching?
3. **Public status for several nodes.** Should the public page query two listed nodes and show disagreement, or keep one answering node with manual switching (current)?
4. **Status page history.** Decided for protocol 15: opt-in per service, the answering node only, a fixed 24 h window, coverage always stated beside availability. Open: longer windows, and whether a page should compare nodes.
5. **Badges.** Decided for protocol 15: a separate per-service 24 h observed badge with availability and coverage, no whole-page figure. Open: whether an embed should name its serving node.
6. **Channel templates.** Is a live preview with sample substitutions wanted, given templates are literal text?
7. **Write target during a partition.** Should editing a monitor assigned to out-of-view nodes ask for confirmation?
8. **Node selection at scale.** Checkboxes suit about six nodes; are regions or tags for nodes expected?
9. **Hierarchy on public pages.** Should a status page ever publish nested sections, given parent links are private configuration today?
10. **Several entry nodes behind a gateway.** A gateway dashboard reaches one node set on its server, so it can't switch when that node is down, and reading another node's history needs direct mode or the CLI. Should the server offer a fixed, operator-set list of entry nodes for the dashboard to choose from? *Superseded by the control plane:* the dashboard server's shared node list (§4.10) is that list, selectable with one sign-in. The question stays only for gateway-only mode, which no current server provides.
11. **Control-plane follow-ups.** Should the dashboard aggregate monitors across registered nodes on its Overview, or keep one selected node at a time (current)? Should an administrator be able to replace a refused node credential in place (the prototype's "Update credential"), which the API doesn't offer yet? Should a node choice survive a reload?
